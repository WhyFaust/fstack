# Реализовать законченное изменение

## Вход и границы

Примени [$fstack:verify](../verify/SKILL.md) к критериям приёмки, [$fstack:no-comments](../no-comments/SKILL.md) к коду.
Для существенной неопределённости выбери нужный приём напрямую либо через
[$fstack:principles](../principles/SKILL.md); [$fstack:plan](../plan/SKILL.md) нужен при неясном порядке
существенных зависимых этапов. Соблюдай порученную область
и инструкции проекта. В поручении подагенту ответственность включает весь
путь от запроса до проверенного результата в выделенной области. В совместной
рабочей копии сохраняй правки соседей и сверяй зависимости на актуальном снимке.
Верни координатору вопрос, если нужен новый владелец или меняется общий контракт.

## Порядок работы

### Восстановить контракт

Прочитай применимые AGENTS.md и принятую инструкцию разработки. Используй
действующие команды проекта; ссылайся на их источник вместо копирования
в параллельную справку, которая может устареть.

Прочитай затронутую реализацию, потребителей, тесты и конфигурацию. Установи
наблюдаемый результат, допустимые входы, ошибки и ограничения совместимости.
Прежде чем брать соседний код за образец, проверь его у действующих потребителей
и в тестах контракта. Временные обходы и устаревшие API могут встречаться рядом
с поддерживаемым путём.
Неопределённость, влияющую на решение, разреши по исходникам или документации.
Если она касается внешнего API или версии зависимости, проверь первичные
источники по профильному навыку. Если такого навыка нет, примени [$fstack:docs](../docs/SKILL.md).
Выдели прежнее поведение, на которое по-прежнему опираются потребители. При смене
формата проверь, какие ранее сохранённые данные должен принимать новый путь.

Выбери простейшее законченное решение исходной задачи. Для исправления сбоя
проверь выбор по [$fstack:debug](../debug/SKILL.md) до реализации. Оцени сложность получившейся
системы: состояния, зависимости, пути отказа и сопровождение. Если новый слой
обслуживает последствия устранимого дефекта, вернись к владельцу причины.
Используй подходящий существующий
механизм проекта, затем возможность платформы и только при конкретной нехватке
новую зависимость. Убирай устаревший путь в пределах поручения. Законченность включает
потребителей, миграцию, настройки и проверки. Малый diff с оставшимся сломанным
вызовом не является более простым решением.

До первой правки свяжи критерии с входами и наблюдаемыми результатами.
Если решения различаются на одном из входов, установи ожидаемый исход по
требованиям, подтверждённому дефекту или уточнению пользователя. Для рискованной
границы укажи инвариант и поведение при отказе.

### Изменить код и потребителей

Держи решения рядом с владельцем данных. Предпочитай явные входы, локальное
изменяемое состояние и прямой поток выполнения. Выделяй абстракцию для реальной
общей ответственности или повторяющегося решения, которое должно меняться вместе.

Не добавляй предполагаемые точки расширения, проходные слои и цепочки запасных
вариантов без поддерживаемого сценария. Сохраняй полезные границы. Используй
инструменты и диапазон версий проекта; новая зависимость требует конкретной
пользы.

При ослаблении проверки или лимита общего механизма проследи всех потребителей.
Если исключение нужно лишь части из них, сохрани прежние ограничения для остальных.
Проверь отдельно разрешённое исключение и случай, где прежняя защита нужна:
успешность основного сценария не подтверждает сохранение этой границы.

Обнови необходимые вызовы и документацию изменившегося контракта. Согласуй
общие интерфейсы с их владельцем, сохрани чужие изменения и исключи постороннюю
уборку и переформатирование незатронутого кода. Связность изменения определяется
одной причиной и законченным результатом, а не числом строк или файлов.
Небольшой исполняемый пример полезен, если проясняет неоднозначный
критерий приёмки; его проверки должны защищать требование, а не повторять код.

Сообщение об ошибке должно помогать вызывающей стороне: назови неудавшуюся
операцию, известную причину и доступный следующий шаг. Непроверенную причину
обозначь как предположение; технические подробности добавляй, когда они помогают
устранить отказ. Сохраняй стабильный формат ошибки, если на него опирается потребитель.

Не ищи по всему проекту дополнительные задачи ради этого изменения и не
создавай серию несвязанных PR. Перед передачей убери собственные временные
логи, отладочный вывод и закомментированные варианты. Сборочные артефакты
добавляй только когда они входят в контракт поставки проекта.

### Предотвратить повтор ошибки

При подтверждённом нарушении найди границу, на которой его можно обнаружить:
тип или API для неверного вызова, штатный линтер для запрещённого импорта,
регрессия через штатную точку входа для ошибочного поведения. Если защита уже
есть, проверь, как вызов её миновал. Убедись, что выбранная проверка выявляет
исходную ошибку и пропускает допустимый случай.

## Проверка и результат

### Подготовить PR или MR

При порученной публикации используй шаблон и формат заголовка проекта. Если
шаблона нет, начни с такой структуры и заполни её фактами:

```markdown
## Зачем
Наблюдаемая проблема, затронутый сценарий и установленная причина.

## Как
Выбранное решение и почему оно устраняет причину. Существенные компромиссы,
совместимость и влияние на производительность, затем состав изменения.

## Проверка
Ревизия, команды или шаги, среда и фактические результаты. Что не проверено
и почему. Для исправления: исходный отказ и результат после изменения.

## Скриншоты
До и после по затронутым платформам или "Внешний вид не меняется".

## Чеклист
- [ ] Изменение соответствует поручению и не содержит посторонней уборки.
- [ ] Проверки выполнены, ограничения явно указаны.
- [ ] Документация и данные для выпуска обновлены, когда требуются.
```

Пиши короткими предложениями, сохраняй одинаковые названия понятий. Описание
должно объяснять окончательное изменение без истории чата. Оставь в нём ревизию,
решающие результаты и ограничения. На длинные логи и материалы прогона дай
ссылки на доступные ревьюеру артефакты. Удали подсказки
шаблона; флажки отмечай только по факту. Для существенного непроверенного
критерия сохрани Draft и назови недостающую проверку. Если нужный CI запускается
только после Ready, соблюдай маршрут проекта и проверь его результат до merge.
При открытии или подготовке GitLab MR проверь исполнителя и ревьюера по
[$fstack:watch-pr](../watch-pr/SKILL.md#назначить-роли-mr).

Одна самостоятельная причина и законченный результат образуют один PR.
Независимые изменения разделяй; для зависимого стека укажи порядок и базу
каждого PR. Не дроби исправление причины на несамостоятельные обходы.
Сохраняй область применимости: расширение исправления с отдельных платформ
или устройств на все требует основания. Будь готов объяснить решение в ревью
и обработай вопросы по [$fstack:feedback](../feedback/SKILL.md). Не добавляй агента или инструмент
автором либо co-author; сохраняй установленную авторскую идентичность пользователя.

### Завершить проверкой

Устрани подтверждённые замечания и повтори затронутые проверки. Если поручен
полный цикл GitLab MR, продолжай по [$fstack:watch-pr](../watch-pr/SKILL.md#полный-цикл-gitlab-mr).

Выполни содержательные проверки приёмки по [$fstack:verify](../verify/SKILL.md), прочитай итоговый
diff и проверь оставшихся потребителей. При необоснованной сложности нового кода
примени [$fstack:simplify](../simplify/SKILL.md). Передай результат, изменения области,
существенные решения, доказательства и ограничения.
