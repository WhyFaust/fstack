# Реализовать законченное изменение

[Каталог · Реализация](../../docs/skills.md#реализация)

Цитата не включает навык. Вне faust-mode применяй только явно вызванные навыки.

До правки восстанови по правилам проекта, коду и потребителям входы, ошибки,
эффекты и совместимость со старыми данными. Свяжи критерий с наблюдением
через штатный вход. Спорный API сверь с [документацией](../docs/SKILL.md),
сбой — с [причиной](../debug/SKILL.md). Сохрани чужие правки и согласуй
изменение общего контракта с владельцем.

Используй подходящий механизм проекта, затем платформы. Исправь причину
у владельца данных, обнови потребителей, миграцию, настройки и документацию.
Вырази смысл [именами и структурой](../no-comments/SKILL.md). Сохрани формат
ошибок, удали временную диагностику. При ослаблении общей проверки или лимита
выяви потребителей, локализуй исключение и отдельно проверь прежнее ограничение.

## Предотвратить повтор ошибки

Закрепи правило ближайшим типом, API, линтером или регрессией через штатный
вход. Если защита была, найди обход. Проверь исходный отказ и допустимый вход.

## Подготовить PR или MR

В активном faust-mode до публикации ветки для GitLab MR открой
[watch-pr](../watch-pr/SKILL.md#полный-цикл-gitlab-mr). Возьми шаблон из ветки
по умолчанию **целевого** проекта, включая запросы из fork.

- В GitHub запроси `pullRequestTemplates`. При поиске по файлам проверь
  `.github/`, корень, `docs/`, затем общий репозиторий `.github` владельца.
  Ищи `PULL_REQUEST_TEMPLATE` без расширения, с `.md` или `.txt`, без учёта
  регистра. Учитывай дефисы вместо подчёркиваний и именованные шаблоны
  в `PULL_REQUEST_TEMPLATE/`.
- В GitLab именованные варианты лежат в `.gitlab/merge_request_templates/`.
  Для шаблона по умолчанию проверь настройки проекта, затем `Default.md` группы,
  экземпляра и проекта без учёта регистра. [Порядок GitLab](https://docs.gitlab.com/user/project/merge_requests/#use-merge-request-templates)

При ошибке чтения сообщи пробел. При подтверждённом отсутствии шаблона используй
«Зачем», «Как», «Проверка». Соблюдай заголовок проекта. Приложи результаты
проверок и скриншоты изменённого UI на затронутых платформах. Удали подсказки,
отметь выполненные пункты, длинные логи приложи ссылками. Передай Markdown
явно в `body`/`description`, для `gh pr create` — через `--body-file`.
Перечитай опубликованное описание и [роли MR](../watch-pr/SKILL.md#назначить-роли-mr).

Разделяй независимые причины, для зависимых PR укажи базу и порядок. Сохрани
авторство пользователя без агента в author или co-author. При существенном пробеле оставь Draft. Если CI требует
Ready, выполни переход по правилам проекта и проверь CI до merge. Устрани
[замечания](../feedback/SKILL.md), [проверь](../verify/SKILL.md) diff и поведение
у потребителей на текущей ревизии. При сопровождении веди до согласованной точки.
