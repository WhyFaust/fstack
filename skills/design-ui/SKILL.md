# Спроектировать и проверить интерфейс

Установи пользователя, его задачу, точку входа, основное действие и наблюдаемый
успех. Уточни только неоднозначность, меняющую решение. Зафиксируй ограничения
стека, бренда, контента и поддерживаемых экранов; не превращай правку элемента
в перепроектирование всего продукта.

## Найти подходящее решение

Прочитай существующие экраны, компоненты, токены, стили и соглашения проекта.
Сохрани привычную навигацию и семантику. Сначала используй текущие компоненты,
затем совместимые возможности платформы; новая библиотека нужна только для
конкретного пробела. Выбирай компонент по действию и поведению: кнопка выполняет
действие, ссылка меняет адрес, поле собирает ввод. Сходный вид не гарантирует
нужную семантику, доступность или совместимость со стеком.

При нехватке примеров используй доступные источники по назначению:

- [Refero](https://refero.design/) для исследования экранов и последовательности
  действий. Объясни, какой приём помогает текущему сценарию; не копируй экран целиком.
- [SL UI Library](https://github.com/SLtowl/sl-ui-library) для поиска подходящих
  компонентов. Проверь их поведение, стек, зависимости и лицензию перед использованием.
- [Agentation](https://www.agentation.com/) для точных замечаний к элементам,
  если он уже доступен и подходит задаче. Без него достаточно селектора или
  снимка с указанием элемента, состояния, ожидаемого и фактического результата.

Эти источники необязательны. Не устанавливай интеграции ради процесса;
недоступность сервиса не блокирует работу с текущей системой. Чужой код,
изображения и шрифты используй только на подходящих условиях, сохраняя атрибуцию.

## Реализовать согласованные состояния

Сначала определи структуру, главное действие и порядок чтения, затем детали.
Используй принятую шкалу типографики и интервалов, токены цвета и одинаковое
поведение однотипных элементов. Учитывай реальные длинные тексты и данные.
Для затронутого потока предусмотрены применимые состояния: начальное, загрузка,
пустой результат, успех, ошибка, недоступное действие и восстановление после сбоя.
Не добавляй состояния без поддерживаемого сценария.

Если поручен только дизайн, передай решение, состояния и критерии приёмки.
Если реализация уже разрешена, продолжай её в текущем стеке; отдельный план
или повторная активация метода не нужны без нового вопроса.
При изменении кода примени fstack:no-comments; для Python добавь fstack:python.

## Проверить фактический интерфейс

По fstack:verify-result выбери достаточные проверки и сохрани первичные артефакты.
Для работающего UI пройди основной сценарий и важные ошибки в фактической версии
существующими средствами проекта; управление браузером выбирай по текущему каталогу.
Осмотри рендер, а не только код или успешную сборку:

- главное действие и уровни информации различимы; конкурирующих акцентов нет;
- размер, длина строки и контраст позволяют читать текст, интервалы показывают группы;
- одинаковые элементы согласованы по виду, названию и поведению;
- на поддерживаемых ширинах, при увеличении масштаба и длинном контенте нет потери
  действий, перекрытий и случайной горизонтальной прокрутки;
- клавиатурный порядок, видимый фокус, доступные имена, подписи и ошибки соответствуют
  семантике; состояние не передаётся одним цветом;
- применимые состояния позволяют понять происходящее и следующий шаг.

Автоматическая проверка доступности дополняет проверку клавиатурой и осмотр.
Если доступен только макет, назови предел: он не подтверждает интерактивность.
Верни изменённый сценарий, существенные решения, проверенные состояния и ширины,
артефакты и ограничения. Заверши после выполнения критериев и разрешения
существенных замечаний; дополнительная итерация должна исправлять конкретный дефект.
