# Выбрать инженерный метод

## Вход и границы

Начни с результата поручения и конкретного риска. Для знакомой небольшой правки
достаточно принятого в проекте решения. Дополнительный метод нужен, когда
остаётся вопрос, от которого зависит корректность или стоимость сопровождения.
Проследи поток от входа через владельцев данных к потребителям и результату.
Сначала ищи подходящее средство проекта, затем стандартной платформы; новую
зависимость оценивай только для оставшейся конкретной нехватки.

## Порядок работы

| Вопрос | Метод |
| --- | --- |
| Какие данные, границы и интерфейс нужны? | fstack:design-change |
| Что изменится у косвенных и внешних потребителей? | fstack:assess-impact |
| Какой результат увидит читатель при конкуренции, повторе или откате записи? | fstack:manage-state |
| Кто владеет ресурсом и освободит его после частичной подготовки или отказа? | fstack:manage-resources |
| Как перевести всех потребителей на новый контракт? | fstack:migrate-contract |
| Есть ли измеримый выигрыш при том же объёме работы? | fstack:measure-performance |
| Чем объясняется прежнее решение? | fstack:trace-history |
| Какая сложность нового diff не нужна для задачи? | fstack:simplify-change |

Если нужный приём уже понятен, переходи к нему напрямую. Выбери только нужные
приёмы и вернись к основному поручению после разрешения вопроса. Каталог не задаёт
обязательный маршрут и не требует загружать все инструкции в контекст.

## Проверка и результат

Проверь решение по трём вопросам: решает ли оно наблюдаемую задачу, охватывает
ли затронутых потребителей, сможет ли другой инженер его безопасно сопровождать.
Число строк и файлов само по себе не отвечает ни на один из них.

Общий код оправдан общим правилом изменения. Для независимо развивающихся
понятий допустимо сходство реализации. Новый слой должен устранять названную
сложность, а не обслуживать предположительный будущий сценарий.

Закрепляй повторяемые механические ошибки схемой, типом, инвариантом или
адресной проверкой. Массовое преобразование сначала проверь на малом фрагменте.
Объяснение важного ограничения сохрани в принятой документации решения. По fstack:verify-result
отдели доказанную необходимость от предпочтения и непроверенной гипотезы.
