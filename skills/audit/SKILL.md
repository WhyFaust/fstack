# Подготовить улучшения кодовой базы

[Каталог · Исследование](../../docs/skills.md#исследование)

Цитата не включает навык. Вне faust-mode применяй только явно вызванные навыки.

На просьбу «улучши кодовую базу» обследуй проект целиком. Начни с дерева,
точек входа, инструкций и прежних находок. Выдели основные части проекта и
как они связаны. В автоматизации тестов это могут быть сценарии и данные,
фикстуры, API-клиенты, UI, диагностика, зависимости, локальный запуск и CI.
Для явно ограниченного запроса возьми порученную область.

Зафиксируй область, целевую ветку, HEAD и merge-base. Включи staged, unstaged и
релевантные untracked-файлы, для существенных входов сохрани хеши. Вне Git
опиши снимок и пределы выводов об истории. Отметь пустой diff и укажи, какую
часть существующей кодовой базы исследовал.

## Найти и расставить проблемы по приоритету

1. В каждой значимой области разбери характерный путь или недавнюю правку.
   От общей функции или ресурса дойди до владельца и в обратную сторону до
   сценариев, на которые повлияет изменение. Для обратного пути используй
   [поиск потребителей](../impact/references/consumers.md).
2. Для ошибки покажи достижимый вход и нарушенный контракт, для долга —
   затронутых потребителей и цену, для слабого теста — пропускаемый отказ.
   Проверь решающие свидетельства сам. Ускорение требует [замеров](../perf/SKILL.md).
   Для ветки отметь происхождение проблемы и основание. Для автотестов сверь,
   какой отказ обнаруживают документированная команда и CI. Фикстуры и выборку
   разбери по [приёмам проверки автотестов](../python/references/aqa.md).
3. Объедини проявления одной причины. Расставь приоритеты по последствиям,
   охвату, уверенности, цене, риску исправления и зависимостям. Отметь гипотезы.
   При повторяющейся ошибке выясни, какие проверки она прошла. Предложи,
   где обнаружить следующий такой случай, и покажи, как отличить его от
   допустимого поведения.
   Проводить можно проверки с известным допустимым эффектом. Не раскрывай
   значения секретов. Сохрани чужие правки.

## Решить, какие улучшения брать в работу

Сам отбери все стоящие предложения по обследованным областям. Ориентир для
первого обзора большого проекта — около семи пунктов. Число определяют находки.
Для каждого дай ID, место в коде, наблюдаемую цену проблемы, ожидаемую пользу,
объём правки и способ проверки. Предложи своё решение: делать сейчас,
отложить до конкретного условия или оставить как есть с объяснением. При нехватке
данных назови замер или наблюдение, которое изменило бы решение.

Покажи, с чего начать и какие пункты зависят друг от друга. Пользователь может
выбрать несколько ID, отказаться от отдельных правок или принять твой порядок.
Если решение зависит от неизвестной границы, задай один-два вопроса по списку.
Например, готов ли пользователь менять общую фикстуру и проверять соседние
наборы в этой итерации. Учти уже заданные ограничения и разрешения. При
делегированном выборе прими технические решения сам. Для порученного обзора
результатом служит список решений. Порученные правки веди по выбранным ID.

## Что включить в отчёт

В отчёте отдели изученные пути от областей, которые видел только в дереве.
Для выбранных правок укажи, как сравнить исходный и новый результат
в тех же условиях. Возьми команду из проекта. Например, `pytest --collect-only`
показывает состав сценариев. Для проверки очистки нужен запуск, в котором
можно наблюдать состояние ресурса после теста.

При следующем проходе сверь прежний список с текущим кодом. Для закрытых
пунктов укажи ревизию и проверенный результат. Открывай проблему повторно
под прежним ID с новыми данными. Для отложенной сохрани причину и условие
возврата в отчёте. Записывай только порученные артефакты.
Если нужен план, передай выбранный ID, зависимости и доказательства
в [scope](../scope/SKILL.md). Перед зависимым этапом проверь контракт в нужной
ревизии и наличие интеграции в целевой ветке.
