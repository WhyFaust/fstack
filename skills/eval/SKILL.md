# Сравнение настроек Codex

Используй только по явному запросу сравнения. Подготовка не разрешает запуск
моделей, живых сервисов или пользовательских задач. Доказательства сверяй
по [$fstack:verify](../verify/SKILL.md).

## Сравнить варианты

1. Зафиксируй варианты, файлы и ревизии, решение, гипотезу, риск регрессии
   и разрешённые ресурсы. Включи вариант без правки и при существенном выборе
   простой достижимый вариант. Заранее задай критерии и независимый эталон
   по требованиям и первичным данным; не показывай их кандидатам.
2. Возьми исходный сбой, близкий новый случай и контрпример. Раздели разработку
   и независимую проверку; подгонка лишает контроль независимости. Для старой
   ошибки восстанови исходный запрос и доступный тогда снимок без поздних
   подсказок, решения и памяти о нём. Для копий укажи источник и отличия среды.
   Сверь снимок с задачей, для дефекта потребуй отказ по нужной причине,
   для контроля — работу исходного сценария. Новую возможность назови явно.
   Свяжи критерии с наблюдениями, укажи пробелы.
3. Сохрани одинаковые запрос, файлы, инструменты, разрешения, модель и настройки
   вне сравниваемой переменной. Изолируй записи: разные worktree могут делить
   стенд или БД. Несколько совместных изменений оценивай одним вариантом.
   Для переноса профиля сверь клиент, плагин, навыки нового чата, имена и
   исполняемые файлы ролей и MCP. Для хуков проверь источник и доверие в Settings
   → Hooks и разрешённое событие. Учётные данные настрой штатно. Отметь
   отсутствующие зависимости и продолжи доступные сценарии.
4. Для fstack из Git checkout используй `tools/fstack/evals/evaluate.py`:
   `--bank PATH validate-corpus --output DIR` сверяет оракулы без моделей, `doctor` проверяет
   клиент и изоляцию, `plan` закрепляет гипотезу и варианты, `run` выполняет
   ограниченные попытки, `calibrate` проверяет оценщика, `judge` сравнивает
   анонимные результаты, `report` сверяет актуальность и даёт рекомендацию.
   Синтаксис — `--help`. Храни корпус и отчёт вне репозитория, выдели пустой
   каталог результата и лимиты. Уже разрешённый ограниченный запуск не согласуй
   повторно. При отказе изоляции зафиксируй ограничение.
5. Дай кандидатам обычный запрос без ожидаемого ответа и победителя.
   Сохрани входы, выходы, действия и все попытки; отдельно отметь отказы среды.
   Разделяй результаты кандидатов, дели только неизменяемый вход. Для
   повторяемости меняй порядок вариантов; число повторов выбирай по расходам,
   разбросу и цене ошибки.
6. Оцени A/B по одинаковой рубрике и первичным данным, включая отдельного судью,
   если нужен. Сам прочитай решающие факты. Сначала проверь исполнение,
   затем самостоятельный выбор решения, после — время и ресурсы. Учитывай
   разброс, повторы и пропуски; скорость не компенсирует нарушенный контракт.
   Спорные баллы модели сверяй с человеком. Для вклада правила сравни вариант без него.
7. Для оркестрации сохрани поручения, параметры и доступные фактические модели,
   reasoning и контекст. Проверь пользу деления и пересечения. Если подагенты
   не нужны, выбор их моделей не проверен; отдельный запуск требует
   поручения с полезным делегированием.

## Отчёт по эксперименту

Дай ID вариантов, сценарии, критерии, наблюдения, замеры и пределы. Отдели
факты от объяснений и соразмерь рекомендацию покрытию: принять, доработать,
отклонить или признать данные недостаточными. Свяжи отчёт с хешами входов
и версией среды. При смене правил, моделей или инструментов затронутые выводы
остаются историческими до проверки.
