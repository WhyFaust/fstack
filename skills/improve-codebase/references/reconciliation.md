# Сверить backlog и передать работу

## Актуальность плана

До повторного аудита, `reconcile` или реализации прочитай индекс и связанные
планы. Не обнуляй статусы и не переписывай историю причины. Для каждого
актуального плана проверь, сохраняется ли проблема, исходное предположение,
потребитель и способ приёмки. Исправленное независимо отметь с доказательством;
сменившийся подход свяжи с прежним ID как замену, не дублируй причину.

Сверяй не только SHA HEAD. Сравни полную записанную основу с HEAD по области
плана и значимым потребителям, затем отдельно staged, unstaged и untracked.
Например, для установленного `<base>` и путей используй `git diff <base>..HEAD`,
`git diff --cached`, `git diff` и `git status --short --untracked-files=all`.
Прочитай релевантные untracked-файлы и сравни исходный локальный снимок.
Полный status сохраняй для контроля выходов за область. Команды без diff
читаемого содержимого не доказывают отсутствие семантического дрейфа.

При изменении существенных мест заново проверь механизм и приёмку, обнови
план и основание по новым фактам. Смена строки при неизменном контракте
не требует перепланирования целиком. Не назначай исполнителя на устаревшее
решение; независимую готовую часть можно продолжать.

## Состояния и зависимости

Различай как минимум: запланировано, в работе, заблокировано, на ревью,
проверено на конкретной ревизии, интегрировано и отклонено. Сохраняй
существующую схему проекта, если она выражает эти различия. У каждого статуса
назови снимок и доказательство; результат review не равен результату verify.

Положительное ревью не означает, что код реализован в целевой ветке или
что условия готовности проверены. Для интеграции укажи фактический commit
и ветку. Для снятия зависимости проверь наличие требуемого результата
в основе исполнителя, а не слово DONE в таблице. Commit можно сверить через
`git merge-base --is-ancestor <dependency-commit> HEAD`; при squash/cherry-pick
или другой истории нужна содержательная проверка эквивалентного контракта.
Если результат сознательно передаётся до merge, запиши точную составную основу,
разрешённый способ переноса и проверку; сам статус ревью зависимость не снимает.

Для заблокированного плана исследуй конкретную причину. Для оставшегося
«в работе» сначала сверь владельца и артефакты через fstack:delegate-work;
не назначай второго писателя по давности записи. Отклонение переоткрывается
лишь при записанном условии или новых первичных данных, меняющих основание.

## Передача в реализацию

Действующее поручение определяет, нужна ли реализация и разрешена ли публикация.
Продолжай уже разрешённую работу без повторного согласования того же плана.
Координатор передаёт готовый вход через fstack:delegate-work: метод
implement-change, debug-failure или refactor-code выбирается по характеру
изменения. Этот процесс использует действующие роли и не создаёт второй
протокол запуска исполнителей.

Передай план целиком либо обеспечь доступ к актуальному артефакту: новый worktree
не содержит незакоммиченный план или исходные локальные правки автоматически.
Проверь необходимые зависимости среды. Worktree изолирует файлы, но не общую
БД, VM, браузер или сервис; назначь владельца ресурсов и безопасную среду
проверки через действующие методы, прежде чем запускать меняющий их сценарий.

Для review и проверки области читай полный diff от зафиксированной основы
исполнителя до HEAD плюс staged/unstaged и релевантные untracked-файлы.
Обычный `git diff` пропускает закоммиченные изменения. Сопоставь каждый
существенный hunk с целью, ограничениями, потребителями и приёмкой, включая
изменения проверок. fstack:review-change даёт независимый вердикт,
fstack:verify-result — доказательства по конкретному снимку. Не дублируй
пригодные прогоны без причины и не приписывай review доказательство запуска.

После исправлений обнови статусы по фактической ревизии. При недоступной
проверке оставь ограничение явно; интеграцию и закрытие зависимостей отмечай
только после подтверждения их собственного условия. В итог `reconcile`
включи: что подтверждено, обновлено, отклонено, заблокировано и готово к работе.
