# Выбрать инженерный метод

Проследи путь от входа через владельцев данных к потребителям и результату.
Для знакомой правки используй решение проекта. При конкретном риске ищи
средство проекта, затем платформы. Новую зависимость оценивай для оставшегося пробела.

| Вопрос | Метод |
| --- | --- |
| Какие данные, границы и интерфейс нужны? | [$fstack:design](../design/SKILL.md) |
| Что изменится у косвенных и внешних потребителей? | [$fstack:impact](../impact/SKILL.md) |
| Как согласовать запись, повтор и восстановление? | [$fstack:state](../state/SKILL.md) |
| Какие порядки событий сохраняют инвариант? Где контрпример? | [$fstack:model-check](../model-check/SKILL.md) |
| Кто владеет ресурсом и освободит его после частичной подготовки или отказа? | [$fstack:resources](../resources/SKILL.md) |
| Как перевести всех потребителей на новый контракт? | [$fstack:migrate](../migrate/SKILL.md) |
| Есть ли измеримый выигрыш при том же объёме работы? | [$fstack:perf](../perf/SKILL.md) |
| Чем объясняется прежнее решение? | [$fstack:why](../why/SKILL.md) |
| Какая сложность diff лишняя? | [$fstack:simplify](../simplify/SKILL.md) |

Открой только нужный метод и затем вернись к поручению.

Оцени результат по задаче, охвату потребителей и возможности безопасного сопровождения.
Объединяй код при общем правиле изменения. Сходство независимых понятий допустимо.
Добавляй слой при доказанной сложности. Размер diff сам по себе ничего не решает.

Закрепляй механические ошибки схемой, типом, инвариантом или адресной проверкой.
Массовую правку начни с проверки фрагмента. Запиши существенное ограничение
в документации решения. По [$fstack:verify](../verify/SKILL.md) отдели необходимость
от предпочтений и гипотез.
