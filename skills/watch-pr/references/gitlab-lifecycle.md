# Довести GitLab MR от Draft до слияния

Применяй этот порядок, когда поручен полный цикл до merge. Один владелец
ведёт MR и ветку до конца активного хода. При делегировании координатор
следит за конечным результатом, общается с пользователем и передаёт новые
факты владельцу. Статус, диагностика, открытие MR или доведение до Ready
сами по себе не расширяют поручение до merge.

## Ранняя публикация

1. Установи исходный проект и ветку, целевой проект и ветку. Найди уже
   открытый MR с этой парой, включая принадлежность source project для fork.
   Продолжай в его ветке. Для нового изменения опубликуй первый содержательный
   коммит и рано открой Draft, чтобы стали доступны MR pipeline и обсуждения.
   Для уже опубликованной ветки используй `glab mr create --draft` с явными
   `--source-branch`, `--target-branch`, заголовком и описанием. Сверь
   возвращённые проект, IID и URL. Для существующего
   MR сохрани его состояние, если поручение или изменения не требуют иного.
2. Публикуй последующие законченные части в ту же source branch. В каждой
   проверь относящиеся к ней изменения. Пока выполняется CI промежуточного
   коммита, продолжай независимую работу. Для запуска CI не создавай пустых
   коммитов и дубликатов MR. После неопределённого исхода push или создания
   MR сначала проверь удалённый ref и список MR.
3. Когда согласованная реализация закончена, обязательные локальные проверки
   пройдены и последний коммит опубликован, переведи Draft в Ready
   (`glab mr update IID --ready`). Соблюдай заданные проектом и пользователем
   условия перехода. Проверь `draft=false`, затем наблюдай финальный CI/CD:
   на некоторых проектах набор обязательных jobs зависит от состояния Draft.

## Финальный CI/CD

Прочитай актуальные head и target, `head_pipeline` MR и список его pipelines.
Установи последний применимый pipeline по его ID, ref, source, project и SHA.
Если Draft пропустил CI, после Ready проверь запуск. При отсутствии актуального
обязательного MR pipeline проверь правила CI и запусти его, если действие
разрешено и GitLab ещё не поставил тот же прогон в очередь. Для merged results или merge train сопоставь
проверяемый результат с исходными коммитами. Проверь требования ветки,
последние применимые попытки обязательных jobs и зависимые downstream pipelines,
если их исход определяет готовность. Обещанное внешнее ревью, обязательный
approval и нерешённые блокирующие обсуждения также входят в приёмку.

Для pending/running продолжай наблюдение с паузами. Для failed изучи первичную
ошибку. Исправимый дефект устрани в той же ветке; доказанный временный сбой
допускает адресный retry в пределах поручения. Для manual, skipped, canceled
или отсутствующего pipeline установи, какой шаг обязателен по конфигурации.
Разрешённый обязательный шаг доведи до результата; для действия с внешним
эффектом, например production deployment, используй его собственные полномочия.
При технической или внешней блокировке сообщи причину, владельца и нужное действие.
Если GitLab ждёт внешнего reviewer или approver, сообщи это пользователю
и жди его решения в пределах порученного наблюдения.

## Одобрение и передача на слияние

По результатам проверок прочитай действующие правила approvals, кандидатов
и уже зачтённые одобрения. При порученном approval и наличии права у текущего
аккаунта одобри проверенный source SHA. При запрете для автора MR или коммита,
обязательном Code Owner или требовании личного ревью оставь решение допустимому
участнику. Используй текущую учётную запись и действующие правила проекта.
После нового push, изменения target, повторного pipeline или сброса approvals
сверь новый снимок и все зависимые условия. Повторяй только актуальные шаги.

Выполни предмержевый отчёт, проверенный merge и подтверждение результата по
[fstack:ship-pr](../../ship-pr/SKILL.md). Команды для SHA, pipeline и approvals
приведены в [справке GitLab API](../../glab/references/api.md#pipeline-и-готовность-к-merge).
