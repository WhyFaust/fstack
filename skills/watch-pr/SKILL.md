# Проверить и сопровождать PR/MR

## Вход и границы

Установи проект, ветки, PR/MR и требуемый конечный результат. Разовый запрос
статуса заканчивается чтением. При поручении довести изменение до готовности
устраняй разрешимые отказы и проверяй результат. Для порученного полного цикла
GitLab от реализации до слияния используй [порядок ведения MR](references/gitlab-lifecycle.md),
включая ранний Draft, Ready, CI/CD и передачу в ship-pr. Открытый MR или один
опубликованный push — промежуточные результаты такого поручения.

В faust-mode наблюдением владеет один исполнитель. При поручении довести
изменение до готовности автор может сам прочитать CI, дождаться результата
и исправить причину сбоя в своей области. Для отдельного запроса состояния
подходит штатный агент Codex с нужным доступом. Сверь head и попытку,
передавай существенные изменения статуса и итог по конкретной ревизии. Координатор принимает итог без повторного опроса CI.

Используй доступного провайдера и правила проекта, включая существующий
git-pr-watch. Не запускай второй watcher поверх действующего. Уточняй только
существенную недостающую границу действий.
Если для операции GitLab нужен переход с MCP на CLI, до первого вызова
прочитай fstack:glab и проверь условия перехода по этому навыку.

## Порядок работы

Прочитай состояние текущей ревизии: checks/pipeline и попытки, обсуждения,
approvals, конфликты, draft, mergeability и требования ветки. Сверь ревизию
каждого обязательного результата с проверяемым изменением. Если проверка относится
к синтетическому merge-коммиту, установи, каким head и base он соответствует.
Успех нескольких jobs не заменяет выполнение всех применимых условий готовности.

При сбое владелец поручения читает первичный лог и сверяет ревизию. Автор
устраняет причину по fstack:debug-failure. Владелец наблюдения без права правки
передаёт подтверждённый отказ координатору. Отдельная независимая проверка
нужна для оставшегося вопроса или по требованию пользователя либо проекта.
Координатор принимает краткий результат с доказательствами, не загружая журнал.
Повторяющаяся ошибка сама по себе не доказывает ни flaky, ни детерминизм;
расположение вне diff не доказывает проблему базы. Повтор обоснуй фактами.

Замечания обработай через fstack:resolve-review. Связанные исправления передай
назначенному писателю и получи необходимые проверки; затем
опубликуй в разрешённой области и перечитай head и актуальные проверки.
Изменение base или опубликованной истории требует соответствующих полномочий.

## Проверка и результат

Передай статус и ссылки: готово, выполняется, заблокировано или нужно решение.
При ожидании избегай частого опроса и сохраняй связь с пользователем. Закончи
при достижении цели, просьбе остановиться или реальной блокировке. Слияние
и auto-merge выполняются через fstack:ship-pr в пределах действующего поручения.
Для задачи на реализацию в GitLab-проекте с разработкой через MR активный
faust-mode уже задаёт полный цикл; явное поручение полного цикла действует так же. Если отдельно поручена только готовность, закончи перед слиянием.
