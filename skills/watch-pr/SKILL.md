# Проверить и сопровождать PR/MR

## Вход и границы

Установи проект, исходную и целевую ветки, PR/MR и условие окончания. Для
разового статуса прочитай текущее состояние. При поручении довести изменение
до готовности устраняй разрешимые отказы и наблюдай до результата. В действующем
faust-mode задача на реализацию в GitLab-проекте с разработкой через MR по
умолчанию охватывает полный цикл. Явное условие остановки имеет приоритет.

За сопровождение одной ветки отвечает один исполнитель. Координатор получает
существенные изменения статуса, поддерживает связь с пользователем и отвечает
за конечный результат. Для перехода с MCP на GitLab CLI используй [fstack:glab](../glab/SKILL.md).

## Порядок работы

Для текущих head и base установи обязательные checks, pipeline и попытки jobs,
блокирующие обсуждения, approvals, конфликты, draft и mergeability. Для
синтетического merge-коммита установи соответствующие source и target. При
сбое проверь ревизию и причину по первичному логу (fstack:debug-failure).
Исправь дефект в пределах поручения, устрани замечания по fstack:resolve-review.
Для временного сбоя обоснуй адресный retry. После push или смены target
перечитай head, зависимые проверки и approvals.

### Полный цикл GitLab MR

1. Найди открытый MR по паре проектов и веток, учитывая fork. Если MR ещё нет,
   опубликуй первый содержательный коммит и создай Draft с явными source и target.
   Сверь проект, IID и URL. Следующие изменения публикуй в ту же ветку. После
   неопределённого результата push или создания прочитай удалённый ref и список MR.
2. Когда согласованная реализация и локальные проверки завершены, опубликуй
   финальный коммит и переведи MR в Ready. Для CLI используй
   `glab mr update IID --ready --repo TARGET_PROJECT`; подтверди `draft=false`.
3. Для финального head сопоставь `head_pipeline` и pipelines MR по ID, project,
   source, ref и SHA. Учитывай последний применимый запуск обязательных jobs и
   зависимых downstream pipelines. При отсутствии обязательного MR pipeline
   после Ready проверь правила CI, очередь и право запуска. Для merge train
   проверь доступный до постановки MR pipeline, затем pipeline поезда.
4. Для manual, skipped, canceled или отсутствующей job установи, требуется ли
   она по правилам проекта. Учитывай полномочия для шагов с внешними эффектами.
   При ожидании внешнего reviewer или approver сообщи пользователю, чей ответ нужен.
   Разрешённый approval давай только для проверенного source SHA и от допустимой
   учётной записи. Соблюдай правила Code Owners, запрет самоодобрения и обещанное
   личное ревью. После сброса approvals сверь актуальные требования.

## Проверка и результат

Сообщи статус для проверенного head, ссылки на CI и обсуждения, оставшийся
шаг или причину блокировки. При порученном сопровождении жди с паузами до
оговорённого результата, просьбы остановиться или реального препятствия.

При поручении полного цикла перед merge координатор сообщает пользователю
ссылку на MR, проверенный source SHA, target, итог и ссылку на pipeline,
approvals и ограничения. Затем выполни слияние и подтверди его по
[fstack:ship-pr](../ship-pr/SKILL.md). При поручении только готовности достаточно статуса.
