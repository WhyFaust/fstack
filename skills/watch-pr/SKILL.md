# Проверить и сопровождать PR/MR

## Вход и границы

Установи проект, исходную и целевую ветки, PR/MR и условие окончания. Для
разового статуса прочитай текущее состояние. При поручении довести изменение
до готовности устраняй разрешимые отказы и наблюдай до результата. В действующем
faust-mode задача на реализацию в GitLab-проекте с разработкой через MR по
умолчанию охватывает полный цикл. Явное условие остановки имеет приоритет.

За сопровождение одной ветки отвечает один владелец: координатор или назначенный
исполнитель. При делегировании координатор получает существенные изменения
статуса, поддерживает связь с пользователем и отвечает
за конечный результат. Для перехода с MCP на GitLab CLI используй [$fstack:glab](../glab/SKILL.md).

## Порядок работы

Для текущих head и base установи обязательные checks, pipeline и попытки jobs,
блокирующие обсуждения, approvals, конфликты, draft и mergeability. Для
синтетического merge-коммита установи соответствующие source и target. При
сбое проверь ревизию и причину по первичному логу ([$fstack:debug](../debug/SKILL.md)).
Исправь дефект в пределах поручения, устрани замечания по [$fstack:feedback](../feedback/SKILL.md).
Для временного сбоя обоснуй адресный retry. После push или смены target
перечитай head, зависимые проверки и approvals.

### Назначить роли MR

При создании Draft определи исполнителя и ревьюера по указанию пользователя,
правилам проекта, владельцу изменения и Code Owners или правилам approvals.
Если исполнитель явно не задан, используй подтверждённого владельца изменения
или автора MR. Для ревью выбери подтверждённого участника проекта, отвечающего
за затронутый участок и допущенного правилами проекта. Сохраняй действующие
назначения. Если подходящего человека установить нельзя, сообщи, какой роли
не хватает, и продолжай доступные шаги.

При создании передай известные назначения в `assignees` и `reviewers` либо
`assignee_ids` и `reviewer_ids`. На существующем MR дополни пропущенные
назначения. Перечитай MR и проверь оба поля после записи и перед Ready.

### Полный цикл GitLab MR

1. Найди открытый MR по паре проектов и веток, учитывая fork. Если MR ещё нет,
   опубликуй первый содержательный коммит и создай Draft с явными source и target.
   Заполни описание по [$fstack:implement](../implement/SKILL.md#подготовить-pr-или-mr)
   с учётом шаблона проекта. Назначь и проверь участников по шагу выше.
   Сверь проект, IID и URL. Следующие изменения публикуй в ту же ветку. После
   неопределённого результата push или создания прочитай удалённый ref и список MR.
2. Когда согласованная реализация и локальные проверки завершены, опубликуй
   финальный коммит, сверь и обнови описание по итоговому diff и текущему head,
   проверь назначения, затем переведи MR в Ready. Результат последующего CI
   добавь после проверки.
   Для CLI используй
   `glab mr update IID --ready --repo TARGET_PROJECT`; подтверди `draft=false`.
3. Для финального head сопоставь `head_pipeline` и pipelines MR по ID, project,
   source, ref и SHA. Учитывай последний применимый запуск обязательных jobs и
   зависимых downstream pipelines. При отсутствии обязательного MR pipeline
   после Ready проверь правила CI и очередь. Если обязательный запуск отсутствует
   и действие разрешено, создай pipeline для MR. Подтверди его ID и связь
   с текущим head. После неопределённого ответа перечитай очередь перед повтором. Для merge train
   проверь доступный до постановки MR pipeline, затем pipeline поезда.
4. Для manual, skipped, canceled или отсутствующей job установи, требуется ли
   она по правилам проекта. Запусти обязательную ручную job по её ID, когда
   поручение и права охватывают её эффекты. Подтверди запуск и дождись результата.
   При ожидании внешнего reviewer или approver сообщи пользователю, чей ответ нужен.
   Если после проверок отсутствует approval, который вправе дать текущий
   исполнитель, передай текущий SHA в шаг одобрения по [$fstack:merge](../merge/SKILL.md). Выполни
   этот шаг до ожидания остальных одобрений.

Для выбора действия по текущему CI передай запускателю fstack команду
`gitlab-ci-action` и снимок в JSON через stdin. Поля `expected_head` и `head`
содержат проверяемый и последний прочитанный source SHA, `expected_target` и `target` —
соответствующие SHA целевой ветки. Поля
`draft`, `pipeline_required` и `may_start` принимают логические значения. В `pipeline`
укажи статус применимого запуска из GitLab. Для подтверждённого отсутствия используй
`absent`, при неполном чтении или незнакомом статусе — `unknown`.
Определяй `may_start` по полномочиям на выполнение CI в выбранном проекте.
Перед запуском конфигурации из fork на ресурсах целевого проекта проверь её изменения
и разрешение на использование этих ресурсов. Для доступной к запуску обязательной
ручной job передай `required_manual_job_id`.
Команда возвращает действие. Перед внешней записью перечитай состояние в GitLab.
При отсутствии запускателя применяй те же переходы по данным площадки.

## Проверка и результат

Сообщи статус для проверенного head, ссылки на CI и обсуждения, оставшийся
шаг или причину блокировки. При порученном сопровождении жди с паузами до
оговорённого результата, просьбы остановиться или реального препятствия.
Если проект требует отчёт о ревью, выполни [`check` для текущих base и head](../review/references/cycle.md)
и учти результат вместе с требованиями площадки.

При поручении полного цикла передай проверенный head в
[$fstack:merge](../merge/SKILL.md), когда завершены ревью и применимые
проверки до слияния. Оставшиеся одобрения устанавливает следующий шаг.
При поручении только готовности достаточно статуса.
