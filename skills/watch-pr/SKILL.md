# Проверить и сопровождать PR/MR

## Вход и границы

Установи проект, ветки, PR/MR и точку остановки. Для разового статуса прочитай
снимок. Для сопровождения устраняй разрешимые отказы до порученного результата.
Границу полного цикла GitLab задаёт [$fstack:faust-mode](../faust-mode/SKILL.md).
Координатор отвечает за итог и связь, у ветки один ведущий. Для перехода на CLI
проверь [$fstack:glab](../glab/SKILL.md).

## Порядок работы

Сверь head/base, обязательные проверки и попытки jobs, обсуждения, approvals,
конфликты, draft и mergeability. У синтетического коммита установи source и target.
При сопровождении начни с конфликтов, затем разбери замечания в области поручения
по [$fstack:feedback](../feedback/SKILL.md), блокирующие первыми. Разрешённые правки
согласуй с владельцем. После push или смены target перечитай head, CI и approvals.
Жди CI после намеченных правок, меняющих ревизию. Для диагностики читай его сразу.
Сбой проверь по первичному логу через [$fstack:debug](../debug/SKILL.md), исправь
дефект или обоснуй retry временного сбоя на актуальном SHA.

### Назначить роли MR

В Draft сохрани назначения, заполни пропуски по поручению, правилам и Code
Owners. Исполнитель — подтверждённый владелец или автор MR, ревьюер — допущенный
ответственный за область. При нехватке роли назови её и продолжи доступные шаги.
Передавай `assignees` и `reviewers` либо `assignee_ids` и `reviewer_ids`.
Подтверди оба поля после записи и перед Ready.

### Полный цикл GitLab MR

1. Найди открытый MR по паре проектов и веток, включая fork. Если его нет, опубликуй
   первый содержательный коммит, создай Draft с явными source и target.
   Примени шаблон по [$fstack:implement](../implement/SKILL.md#подготовить-pr-или-mr),
   сверь участников, проект, IID и URL. Публикуй правки в ту же ветку.
   При неопределённом push или создании перечитай ref и MR.
2. После локальных проверок опубликуй финальный head, обнови описание по diff,
   проверь назначения и переведи MR в Ready. Для CLI используй
   `glab mr update IID --ready --repo TARGET_PROJECT`, подтверди `draft=false`.
   После CI внеси результат проверки.
3. Сверь `head_pipeline` и MR pipelines по ID, project, source, ref, SHA.
   Проверь последние применимые jobs и downstream. Если обязательного MR
   pipeline нет после Ready, сверь правила и очередь, запусти его при полномочиях,
   подтверди ID и head. При неопределённом запуске перечитай очередь. Для train
   проверь доступный MR pipeline до постановки, затем pipeline поезда.
4. Для manual, skipped, canceled и отсутствующих jobs установи обязательность.
   Разрешённую обязательную ручную job запусти по ID, подтверди и дождись.
   После проверок выполни доступный текущему исполнителю approval по
   [$fstack:merge](../merge/SKILL.md) до ожидания остальных. Назови нужного ревьюера или approver.

Для `gitlab-ci-action` передай JSON через stdin. `expected_head` и `head`
содержат ожидаемый и последний source SHA, `expected_target` и `target` —
соответствующие target SHA. `draft`, `pipeline_required`, `may_start` логические.
В `pipeline` передай статус GitLab, подтверждённое `absent` или `unknown`
при неполном чтении или незнакомом статусе. Для доступной обязательной ручной job укажи
`required_manual_job_id`. `may_start` требует прав на эффекты CI. Перед fork CI
на ресурсах целевого проекта сверь конфигурацию и полномочия. Перед записью
перечитай GitLab. Без запускателя следуй тем же переходам.

## Проверка и результат

Дай head, ссылки на CI и обсуждения и оставшийся шаг. Сопровождай с паузами
до результата, просьбы остановиться или блокировки. При требовании отчёта
выполни [check](../review/references/cycle.md) для текущих base и head.
Для полного цикла передай проверенный SHA в [$fstack:merge](../merge/SKILL.md)
после ревью и применимых проверок.
