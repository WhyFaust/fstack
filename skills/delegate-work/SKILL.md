# Делегирование работы

## Вход и границы

Установи требуемый исход: ответ, исследование, план или изменение; ограничения,
разрешённые действия и наблюдаемые критерии. Используй поручение и доступные
факты, спрашивай пользователя только о существенном выборе, который нельзя
установить по источникам, или недостающем разрешении. Простой ответ из известных
данных дай сам без плана, ролей и прогонов.

Существенное исследование, реализацию и прогоны передавай исполнителям.
В активном ходе продолжай разрешённую работу до выполнения критериев либо
конкретной блокировки, не останавливайся на предложении следующего уже
порученного шага. Этот протокол не создаёт фонового scheduler и не гарантирует
продолжение после окончания хода клиента.

## Порядок работы

### Выбрать ближайший результат

Назначай следующий шаг только для незакрытого критерия или блокирующего вопроса.
Если ближайший результат имеет одну область ответственности, дай одно узкое
поручение. Конкретное исправление с известным требованием передавай сразу
coder: нужный код и детали он изучит сам. Отдельный auditor нужен для
неизвестного, которое блокирует решение.
Подтверждённые факты передавай ссылками; смена роли не требует заново добывать
их широким поиском. Чтение затронутого кода автором и независимого diff reviewer
сохраняется.

При существенных зависимых результатах используй
[fstack:plan-work](../plan-work/SKILL.md); не создавай отдельный план для обычных
шагов одного ограниченного поручения. До изменения свяжи критерии с проверками
по [fstack:verify-result](../verify-result/SKILL.md). При существенном риске общего
контракта закончи оценку потребителей по fstack:assess-impact до реализации.
Координатор хранит краткий порядок, владельцев, снимки, состояния и следующий
вопрос. Отдельный файл, таблица или формуляр не обязательны.

Координатор вызывает инструменты назначения, связи и ожидания исполнителей,
принимает их результаты и общается с пользователем. Поиск файлов, чтение кода,
diff и логов, shell, Git, API проекта, запуск и опрос CI относятся к поручениям,
даже когда команда короткая. Не выполняй их как "независимую работу" между
ответами исполнителей. Для нового вопроса назначь владельца; при занятом лимите
дождись свободного места, не подхватывай выполнение сам.

Чтение входного метода и конфигурации ролей для назначения допустимо.
Ещё одно узкое исключение: точный pack/stage памяти выполняет координатор,
поскольку хук принимает операцию только от главного агента текущего хода.
Сбор фактов, поиск дубликатов и текст кандидата поручай исполнителю.

| Роль | Поручаемый результат |
| --- | --- |
| auditor | Факты о коде, требованиях, Git и CI без правок; чтение статуса и ожидание существующих pipeline по поручению |
| coder | Законченное изменение с авторскими проверками; Git-записи, подготовка и разрешённая публикация PR/MR в назначенной области |
| reviewer | Независимое чтение diff и вердикт по требованиям и доказательствам |
| verifier | Конкретный пробел доказательств, недостающий прогон или отдельная среда проверки |
| allure_analyst | Числа, попытки и причины отказов определённого Allure-прогона |

### Назначить владельца

До первого запуска в текущем клиенте установи доступные способы назначения роли,
передачи контекста, связи, получения результата и ограничения ресурсов.
Сверь модель и reasoning с TOML роли по
[политике выбора](references/model-routing.md). Используй только доступные
поля инструмента: имя роли в тексте не доказывает загрузку TOML. Повторная сверка
нужна при смене клиента, конфигурации или возможностей, а не перед каждым
одинаковым поручением. Не меняй выбранные настройки, права или лимиты ради обхода
ограничения. При исчерпании ёмкости продолжай последовательно после освобождения
завершённых потоков, не дублируя активных владельцев.

Для нового независимого поручения выбирай свежий контекст, например
fork_turns="none", если поддерживается. Передавай самодостаточное задание:
результат и критерии, ревизию и нужные факты со ссылками, разрешённые файлы,
действия и ресурсы, ответственность и подтверждённые параметры исполнителя.
Добавь контакт и доступный способ связи, зависимый вход, условия досрочного
сигнала и возврат результата по verify-result. Историю и тела навыков не копируй.
Исполнитель сам выбирает метод под ближайший результат и предметные дополнения;
очевидный метод применяется прямо, select-skills нужен только при неясном выборе.
Новый контекст читает собственные инструкции; уже загруженный текст в том же
контексте повторять не нужно.

Если в поручении разрешены методы fstack, передай свежему исполнителю точный
доступный ему путь к [каталогу установленного пакета](../../docs/skills.md),
разрешение применять нужные методы в пределах поручения и полные имена или
ссылки на методы, явно затребованные пользователем. Если список клиента скрывает
метод, исполнитель открывает его по ссылке из этого каталога. При неясном выборе
оттуда же открывает fstack:select-skills. Если путь недоступен, исполнитель
сообщает ограничение и продолжает доступную часть поручения. Передача каталога
сама по себе не включает faust-mode и не разрешает установку пакета.

### Развести параллельные поручения

Запускай одновременно только работу, которая может идти на подтверждённых
входах и не конфликтует по изменяемым ресурсам. Для каждой правки закрепи
файлы и ресурсы за одним писателем. Если несколько поручений меняют или
используют общий интерфейс, назначь одного владельца его изменения. До
зависимых правок согласуй с владельцем и потребителями сигнатуры, форму данных,
ошибки и побочные эффекты. Передай потребителю подтверждённый контракт и его
снимок. Он может начать работу по этому входу, а проверку совместной работы
выполняет с зафиксированной реализацией. При изменении входа приостанови
зависимую работу до сверки нового снимка и сохрани ход независимых задач.

Выделяй отдельные Git worktree, когда параллельным поручениям нужны собственные
ветки, индекс или версии изменяемых файлов в одной рабочей копии. Независимое
чтение одного снимка может использовать общее дерево. Worktree не изолирует
общую VM, БД или браузер. Выдели независимый экземпляр либо выполняй операции
с общим изменяемым ресурсом последовательно у его владельца.

Исполнители сохраняют назначенные границы и владельцев и не запускают агентов.
Нового писателя назначай лишь после подтверждённой остановки прежнего и сверки
его правок, артефактов и ресурсов.

### Передавать сигналы и ждать события

До фонового запуска установи способ получения результата: синхронный возврат,
блокирующее ожидание либо доставка события. Без ожидания и доставки используй
доступный синхронный способ. При реальном запрете или отсутствии делегирования
назови ограничение, выполни минимальную разрешённую работу последовательно
и обозначь оставшийся пробел независимости.

В поручение включи: исполнитель возвращает один краткий итог по verify-result;
раньше сообщает о нужном решении, реальной блокировке или изменении входа другого
поручения. Сначала результат или вопрос, затем только нужные факты и ссылки.
Зависимость передаётся назначенному контакту доступным каналом либо через
координатора. Без связи в ходе работы сохрани артефакт; если нужен ответ для
продолжения, верни blocked с фактом, ссылкой и конкретным недостающим решением.

Для продолжения работы используй операцию, которая запускает ход существующего
исполнителя, а не только ставит сообщение в очередь. Например, в Codex
MultiAgentV2 followup_task запускает ход неактивного исполнителя, send_message
лишь передаёт сообщение. Сверяй контракт текущего инструмента, не только имя.
Постановка сообщения в очередь не доказывает доставку.

Пока поручение активно, решай независимые вопросы координации либо блокирующе жди.
Пробуждение ожидания может означать сообщение, ввод пользователя или timeout,
а не готовый результат: прочитай доставленный итог либо доступный артефакт.
После timeout продолжай ожидание без циклов списка/статуса и без подхвата чужой
работы. Разовая адресная сверка нужна при реальном дедлайне, признаке сбоя
доставки или неизвестном исходе внешней записи. При потере канала назначь момент
сверки; неизвестный исход сохраняет владельца и блокирует его замену.
Перед повтором внешней записи сначала разрешённо прочитай целевое состояние;
установи причину и допустимость повтора. Отказ доступа не обходи другим путём.

## Проверка и результат

### Принять причину и память

Для исправления сбоя потребуй цепочку: наблюдение, нарушенное условие,
причинный механизм, изменение этого механизма и исходная проверка после него.
Зелёный прогон после подавления исключения, увеличения ожидания или обходного
скрипта не закрывает критерий устранения причины. Если причина неизвестна,
верни исследовательский вопрос исполнителю. Если причина вне полномочий,
зафиксируй конкретную блокировку; временное смягчение требует отдельного
явного запроса и не заменяет исправление.

Если для решения нужен контекст проекта из памяти, используй уже полученный
статус хука и поручай только недостающее чтение по use-memory. Добавь этот вопрос
в поручение действующего владельца, если он может его закрыть. Исполнитель
возвращает нужные ограничения с источниками либо точный статус недоступности.
Для прямого ответа из имеющихся данных отдельная проверка памяти не нужна.
Оценка результата хода и обработка токена сохраняются по use-memory.

В итог поручения включай устойчивый новый вывод с основанием и областью либо
отсутствие такого вывода. Координатор принимает один кандидат, поручает проверку
близких записей и выполняет pack/stage по use-memory. При исправлении правила
нужен supersedes. Отчёт о текущем прогоне не является долговечной записью.
Stage подтверждает подготовку, фактическую запись применяет Stop. Если хук
не выдал токен, не изобретай его и не обходи проверку: поручай диагностику
установки и событий, обозначь невозможность автоматической записи.

### Принять изменение

Сопоставь краткий итог с критериями, текущим снимком и владельцем; большие diff,
логи и отчёты оставляй по ссылкам. Укажи только навыки, повлиявшие на решение,
действие или проверку, и их вклад. Для существенного изменения назначь свежего
reviewer без истории автора и ожидаемого вердикта. Он сам читает требования,
diff и решающие первичные данные. Отдельный verifier нужен лишь для оставшегося
прогона, среды, независимого объёма или конкретного сомнения по verify-result;
не назначай его только ради названия роли. Независимые проверки могут идти
параллельно по одному зафиксированному снимку при независимых ресурсах.
Для reviewer используй ограничения записи, если клиент их поддерживает;
иначе явно запрети правки и сверь неизменность снимка, не обещая read-only sandbox.

Подтверждённый дефект верни автору в тот же поток как конкретную коррекцию.
Автор обновляет затронутые доказательства; тот же reviewer проверяет delta
и связанные риски. Перенос незатронутых результатов и обязательные повторы
определяет verify-result. Поздний итог старой ревизии не принимай как текущий
без этой сверки. Каждый новый запуск должен закрывать оставшийся вопрос,
а не повторять весь процесс автоматически.

Закончи по критериям verify-result, передай итог и ограничения. Исследование,
план или подтверждённый no-op заканчиваются своим результатом без искусственного
кодирования, ревью и прогонов другой области. Блокирующий вход останавливает
только зависимую часть. Освободи завершённые потоки доступным способом.
Для паузы используй fstack:checkpoint-task, для продолжения — fstack:resume-task.
PR/MR сопровождай по fstack:watch-pr в пределах поручения; публикация и слияние
требуют разрешения.
