# Проверить конкретное изменение

## Вход и границы

Примени fstack:verify-result к доказательствам. Для существенного вопроса
о модели, границе или состоянии выбери приём через fstack:engineering-principles.

Зафиксируй ревизию либо однозначный снимок проверяемых файлов. Для PR/MR
сохрани base и head, сверь набор изменённых файлов с diff, который показывает
площадка. В Git для изменений ветки с момента расхождения используй
`git diff <base>...<head>`. Для переданного патча или незакоммиченных правок
проверяй именно предоставленный снимок, включая указанные изменения вне HEAD.
Проверяй исходники самостоятельно. Исправления передавай владельцу снимка.
При делегировании получи требования, снимок и первичные данные в свежем
контексте без ожидаемого вердикта. Сообщи координатору, если унаследовал
историю автора или для независимой оценки не хватает доступа.

## Порядок работы

### Восстановить требование

При смене снимка сообщи координатору. Прочитай поручение, инструкции проекта, фактический diff, окружающий код
и потребителей. Отчёт исполнителя помогает найти доказательства, но не задаёт
вердикт. Проверь результат и границы поручения.

Приоритизируй достижимые риски: изменение поведения, совместимость контрактов,
жизненный цикл ресурсов, параллелизм, передачу ошибок и силу тестов. Если diff
затрагивает существенную границу доверия или пользователь явно просит проверить
безопасность diff, проследи по коду субъекта, его права, вход, проверку доступа
и операцию над ресурсом. Для замечания установи, как изменение влияет на достижимость
нарушения или его последствия. При недостатке данных укажи, чего не удалось
проверить. Дополнительное усиление действующей защиты обозначь как рекомендацию.
Для запуска недоверенного кода используй изолированную среду без сети, секретов
и общих ресурсов, с ограниченными правами на файлы и лимитами ресурсов.
При отсутствии изоляции ограничь проверку чтением исходников.
Для последствий за пределами diff примени fstack:assess-impact, если они существенны.

### Подтвердить каждое замечание

Назови вход, условия и нарушенный контракт. Предпочитай минимальное практическое
воспроизведение с ожидаемым и наблюдаемым результатом в изолированных разрешённых
ресурсах. Не занимай чужое окружение.

Если запуск недоступен, допустимо достаточное статическое доказательство:
достижимый путь, запускающий сценарий и механизм отказа. Укажи, почему запуск
не выполнен. Подозрительный шаблон без доказанного пути остаётся гипотезой.
Если причина существовала до изменения, проверь, делает ли diff этот путь достижимым,
расширяет ли последствия или нарушает заявленный критерий.

Оцени первичные артефакты по fstack:verify-result. После исправления
проверь изменённую область и связанные риски. Повторяй полное ревью при
расширении риска или по требованию проекта.

Проверяй изменения тестов против требований, независимо от заявленного покрытия.
Для исправления сопоставь заявленную причину с механизмом diff и исходным
сценарием. Если ошибка лишь скрыта, вход обойдён или проверка ослаблена,
критерий исправления не выполнен даже при зелёном CI. Отсутствие причинных
данных обозначь пробелом доказательств, а не выдуманной причиной.
При ревью Python-тестов примени критерии fstack:python к структуре и assertions в фактическом diff.
Для конфигурации и генерируемого объекта прочитай сам объект и его потребителя.

## Проверка и результат

### Вернуть пригодный для исправления вердикт

Объедини проявления одной причины. Для замечания дай приоритет по последствиям,
место, сценарий, нарушение, доказательство и минимальную коррекцию. Необязательные
упрощения и замечания по стилю, включая fstack:no-comments, отдели от нарушений
поведения. Для каждого дефекта покажи, что он затрагивает действующий контракт.

Передай вердикт по verify-result с ревизией, проверками и пробелами. Отсутствие
замечаний — допустимый результат. Ревью не разрешает слияние, публикацию или развёртывание.
