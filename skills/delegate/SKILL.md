# Делегировать работу

Связную правку ведёт один владелец от причины до проверки. Отдельный агент
полезен, когда может параллельно выдать самостоятельный результат или независимо
проверить решение. Координатор отвечает за итог и держит связь с пользователем.

## Выбрать исполнителя

Установи, что агент должен вернуть, какие у него права и от чьих данных он
зависит. Независимые поручения запускай параллельно в пределах слотов клиента.
Для общего файла, ветки или базы назначь одного писателя. Если делишь правку
по контракту, согласуй сигнатуры, ошибки и эффекты. Разнеси индексы Git по
worktree. Перед параллельными сборками и тестами оцени доступные CPU, память
и ограничения общего окружения. Разведи конкурирующие прогоны по времени.
Общий браузер и изменяемый стенд используй по очереди или изолируй сессии и данные.

По умолчанию используй настройки клиента и наследование от родителя. Явный выбор
пользователя для исполнителя имеет приоритет. Меняй глубину рассуждения, когда
этого требует само поручение. Для короткой сверки её можно снизить, для поиска
причины через несколько систем — повысить. Если причины могут взаимодействовать,
попроси проверить и отдельные причины, и их совместное действие. Выбери глубину
по сложности этой проверки.
При отклонении параметров сверь схему клиента и укажи подтверждённую замену.
Если запуск недоступен, выполни доступную часть и укажи, где требовалась
независимая проверка.

В Codex используй `fork_turns="none"` для свежего контекста. Передавай `model`
и `reasoning_effort` только для нужных переопределений по схеме клиента.
Если исполнителю нужна вся история, используй `fork_turns="all"` с унаследованными
настройками. Если клиент требует ID модели для смены глубины, используй модель
из явного выбора или подтверждённых настроек. Если ID неизвестен, оставь глубину
клиенту. Независимому ревьюеру дай исходные требования, снимок и данные на чтение
без вердикта автора.

## Передать поручение

Первой строкой дай абсолютный путь к [правилам исполнителя](worker.md) в
установленном пакете. Затем укажи результат, критерий приёмки, ревизию, границы
правок и нужные источники. Выбери один сценарий, если он подходит:
[реализация](workflows/implement.md), [ревью](workflows/review.md) или
[сопровождение PR/MR](workflows/follow-pr.md). Если файл исполнителю недоступен,
передай нужные шаги текстом. При продолжении достаточно новых данных.
Токен записи памяти остаётся у координатора.

Как только готов вход для зависимого поручения, передай его с ревизией.
При изменении контракта сообщи зависимым владельцам до дальнейших правок.
Замечание верни тому, кто менял код. В Codex `followup_task` продолжает работу
неактивного агента, `send_message` доставляет сообщение работающему.

## Принять результат

Пока агент работает, выполняй доступную независимую часть. Если ожидание истекло,
проверь состояние агента и его артефакты. Дождись работающего. Если связь потеряна,
установи, какие записи успели пройти, и передай оставшуюся работу новому владельцу
или заверши её сам. Слот освобождай, когда результат или передача подтверждены.

Сверь дифф, ревизию и [доказательства](../verify/SKILL.md) с критерием поручения.
Для исправления повтори исходный сценарий по [debug](../debug/SKILL.md).
При смене ревизии повтори затронутые и обязательные проверки. Для полного цикла
GitLab один владелец [сопровождает MR](../watch-pr/SKILL.md) до разрешённого перехода.

В подключённом проекте вне Plan сведи подтверждённые поправки и источники по
[правилам памяти](../memory/SKILL.md). Координатор выбирает одну операцию
`stage`, исполнитель отвечает на свой хук через `report`.
Пользователю передай результат, существенные пробелы и ограничения проверки.
