# Команды памяти

Одобренные хуки работают в обычном чате. Команды `/faust-mode` и
`/faust-mode-off` переключают только координатора. В Plan пропускай
автоматическую запись и `skip`.

- [Чтение и статус](#чтение-и-статус)
- [Подключение и отключение](#подключение-и-отключение)
- [Переход с прежнего формата](#переход-с-прежнего-формата)
- [Запись из чата](#запись-из-чата)

Запускай `bin/fstack memory` из каталога подключённого проекта.
Путь ниже обозначает готовый бинарник в установленном пакете fstack.
На Windows это `bin/fstack.exe`, вызываемый через PowerShell.
Python, Rust и Cargo пользователю не нужны. Бинарник находит ресурсы рядом
с собой; для отдельной сборки разработчика есть `fstack --package ROOT memory ...`.

## Чтение и статус

```text
"/path/to/fstack/bin/fstack" memory status
"/path/to/fstack/bin/fstack" memory search "условия выпуска" --limit 5
"/path/to/fstack/bin/fstack" memory show ID
"/path/to/fstack/bin/fstack" memory history ID --limit 5
"/path/to/fstack/bin/fstack" memory diagnostics
"/path/to/fstack/bin/fstack" memory inbox
"/path/to/fstack/bin/fstack" memory shared search "язык отчёта" --limit 3
"/path/to/fstack/bin/fstack" memory shared show ID
```

`search` возвращает полные записи текущего проекта. `--limit` принимает 1–50,
по умолчанию 5; запрос ограничен 500 символами. Поиск использует первые 20
уникальных значимых слов запроса в заголовке и теле, не произвольное выражение FTS. Если выдача пуста
или шумна, следуй [порядку уточнения](retrieval.md#уточнение-поиска).
`show` читает текущую доступную запись по её ID. Не вызывай его повторно,
если полный актуальный текст уже получен в `search`.

`history` читает цепочку подтверждённых версий, включая заменённые, по ID
любой доступной версии в текущем проекте. Значение `--limit` от 1 до 10,
по умолчанию 5. `entries` начинается с заданного ID, дальше идёт обход по
ближайшим связям, сначала к предшественнику, затем к преемникам в порядке ID.
`changes` содержит пары `from`/`to` только для связанных версий в выдаче,
старые и новые значения изменённых свойств, а для тела одну область
замены строк с номером первой строки. `truncated` означает, что есть ещё
доступные связанные версии. `source` остаётся полем заметки для сверки по
первичным данным. Забытые записи и Inbox исключены, удаление разрывает
связи с забытой версией.

`diagnostics` показывает последний технический этап за час и количество
ожидающих операций текущей рабочей папки и привязки. `staged` соответствует
приёму в `PostToolUse`, `pending` соответствует передаче из `Stop` в
очередь применения. `applied` появляется после подтверждения применения
в очереди, а `failure` означает ошибку попытки. `capture` означает выдачу
токена, `review` напоминание, `unconfirmed` завершение без принятой операции,
`skipped` обработанный `skip`, `cancelled` смену режима или привязки во время
попытки, `discarded_forgotten` завершение операции над забытой записью.
`phase: null` означает отсутствие доступного наблюдения. Команда не
показывает содержимое операций и не восстанавливает события прежних версий.

## Подключение и отключение

На первом обычном запросе главный агент получает контекст от хука. Если хук
просит `ensure --turn TOKEN`, выполни указанную команду вне Plan до основной
работы. Ответ хука даст инструкции записи в том же ходе. Для проверки
того же пути из терминала запусти `memory ensure` в рабочей папке, затем
`memory status`. `memory vault` показывает, какой vault обнаружен. При нескольких
вариантах выполни `memory vault --set PATH` с выбранным рабочим vault. Следующий
новый проект подключится автоматически. В vault появятся папка и страница
с коротким именем рабочей папки. Если имя уже занято, хук подберёт свободное
имя с номером, например `api-2`. Явный `init` нужен для ручного имени,
выбора режима или восстановления отключённого проекта. Vault должен содержать каталог конфигурации `.obsidian`. Git worktree
одного репозитория используют одну привязку. Для папки вне Git привязка действует
из этой папки. Хуки используют бинарник из установленного пакета,
без поиска интерпретатора или программы в PATH.

```text
"/path/to/fstack/bin/fstack" memory init --vault "/path/to/vault" --repo "/path/to/project" --project my-project --mode auto
```

Первое подключение по умолчанию использует `auto`. Codex сам сохраняет
долговечные записи по текущей работе. Для ручной проверки всех кандидатов
выбери `--mode inbox`. Повторный `init` без `--mode` использует уже выбранный
режим. Открой новый чат и одобри хуки fstack в меню `/hooks`
или через **Settings → Hooks** в Codex Desktop. Подключение локально для
устройства. Используй одинаковый `--project` на каждом устройстве, где
работаешь с этой памятью.

По явному запросу на отключение проверь текущую привязку через `status`.
Команда ниже выключает память текущего проекта на этом устройстве. Следующие запросы
учитывают это решение до явного `init`.

```text
"/path/to/fstack/bin/fstack" memory disable
```

## Переход с прежнего формата

Обнови fstack на всех устройствах, где Codex читает или записывает этот vault.
Для именованных страниц и JSON-отметок удаления требуется новая версия.
Дождись получения файлов через синхронизацию и запусти из подключённого
проекта первую фазу.

```text
"/path/to/fstack/bin/fstack" memory migrate
```

Команда готовит именованную страницу в каталоге прежней `Project.md`,
связывает с ней записи, переносит подтверждения в заметки и переводит
отметки `Forgotten` в JSON рядом с заметками. После синхронизации обновлённых
файлов, включая JSON, на всех устройствах запусти вторую фазу.

```text
"/path/to/fstack/bin/fstack" memory migrate --prune-legacy
```

Она удаляет перенесённые отметки, опустевшие каталоги `Approved` и `Forgotten`
и прежнюю страницу, когда её содержимое перенесено и записи связаны с новой.
При неполной доставке дождись синхронизации и повтори обе фазы в том же порядке.
Во время переноса работай с одним устройством и закончи правки заметок на
других устройствах до запуска команды.

## Запись из чата

Для поправки проекта подставь в префикс, выданный хуком, тему и полное
правило в отдельных аргументах. Например, `memory stage --turn TOKEN
--correction 'Проверка релиза' 'Проверять установку релиза в чистом профиле.'`
выполняется одной командой. Для коротких полей из слов, пробелов и обычной
пунктуации допускаются и двойные кавычки. Если хук просит повторить команду,
используй одинарные кавычки или передай сложный текст через `pack`.
При исправлении прежнего правила добавь
`--supersedes ID`. Сложный текст с переводом строки, операцию другой области
или другие действия передавай через `pack`.

Передай один объект JSON в `pack` через стандартный ввод в UTF-8. Команда
вернёт строку base64url в JSON. Возьми содержимое строки без JSON-кавычек
и вызови отдельную команду в той же рабочей папке.

```bash
"/absolute/path/to/fstack/bin/fstack" memory stage --turn TOKEN --payload BASE64URL
```

На Windows используй форму PowerShell.

```powershell
& "C:\absolute\path\to\fstack\bin\fstack.exe" memory stage --turn TOKEN --payload BASE64URL
```

Возьми готовый префикс команды и токен из контекста хука. Подставь только
строку из `pack`. Хук принимает один вызов без пайпа, перенаправления
и других команд. Результат `{"staged": true}` подтверждает проверку команды.
Операцию принимает проверенный `PostToolUse`, а применяет `Stop`, в том числе
после продолжения хода. Если `Stop` напомнил об оценке памяти, выполни её
с последним токеном `UserPromptSubmit`. Повтор той же
операции допустим. Другую операцию в том же ходе `PostToolUse` отклоняет с
причиной, сохраняя первую. Второй операции нужен новый ход. После приёма в `PostToolUse` временный отказ или отсутствие первого `Stop`
оставляет операцию в очереди до истечения срока
токена. Следующий обычный `Stop` может повторить её в том же чате, рабочей
папке и неизменной привязке. Токен и base64url
предназначены для вызова инструмента, в ответе пользователю их не повторяй.

Пример объекта для `pack` после проверки решения

```json
{
  "action": "remember",
  "candidate": {
    "kind": "decision",
    "title": "Условия публикации пакета",
    "body": "Для выпуска этого пакета публикуем только из main после матрицы Windows и Ubuntu. Решение подтверждено владельцем; условия сверены с workflow выпуска."
  }
}
```

`action` принимает `remember` для обоснованной долговечной записи
или `draft` для кандидата, который нужно проверить. `kind` принимает
`decision`, `preference` или `correction`.
Если новых долговечных знаний нет, выполни `memory stage --turn TOKEN --skip`.
Прежняя форма `{"action":"skip"}` через `pack` и `stage` также поддерживается. Поля текста и причины для `skip` не допускаются.
Подтверждение не создаёт заметку или Inbox-кандидата и удаляется из очереди
при `Stop`. В Plan не вызывай `stage`, включая `skip`.
В `candidate` можно передать `source` со ссылкой и `supersedes`
с идентификатором предыдущей записи. Для обработки Inbox и удаления передай
`{"action":"approve","id":"ID"}` или `{"action":"forget","id":"ID"}`.

Для явной просьбы «во всех проектах добавляй журнал сборки» подготовь общий
кандидат. Область указывается на уровне операции.

```json
{"action":"remember","scope":"shared","candidate":{"kind":"preference","title":"Журнал сборки","body":"По просьбе пользователя прикладывать журнал при передаче результата сборки во всех проектах."}}
```

Подай его через обычные `pack` и `stage`. Общие `draft`, `approve` и `forget`
используют ту же область. Операция без `scope` относится к текущему проекту.
Для чтения добавь к `memory shared` команду `search`, `show`, `history` или `inbox`. Команды работают в проекте того же vault.

В терминале владелец может вызвать `remember` с объектом `candidate` через
stdin, `approve ID` и `forget ID` напрямую. `remember` учитывает режим
привязки. Записи и Inbox относятся к привязке текущей папки.
