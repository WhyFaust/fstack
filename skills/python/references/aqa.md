# Улучшение Python-автотестов

Выбери приём под конкретное затруднение. До правки зафиксируй, как оно проявляется и какая проверка покажет разницу.

## Сценарии и фикстуры

- Блокируй следующий шаг, если нарушено его предусловие. Например, при найденном одноимённом объекте остановись до создания нового. Независимые расхождения результата можно собрать вместе. Проверь обе ветви, включая отсутствие лишней записи при отказе.
- Если сценарии отличаются только входом и ожидаемым результатом, вынеси различия в параметры. Дай вариантам понятные ID. Сверь состав кейсов через `pytest --collect-only -q` до и после, включая выборку по маркерам. Проверь, что каждый вариант сохранил свои утверждения и связь с кейсом в отчёте. Сбор подтверждает состав, исполнение проверяет поведение.
- Размести общую фикстуру в ближайшем `conftest.py`, доступном всем её потребителям. Раздели срок жизни дорогого подключения и изменяемых данных теста. Для нескольких объектов с разными свойствами используй фабрику, которая учитывает каждый созданный ресурс для очистки. Проверь сбой посередине подготовки и следующий сценарий на том же стенде.
- При тестировании клиента подставь транспорт с реальной сигнатурой вызова, например через `autospec`. Проверь обработку ошибки через публичный метод клиента. В сквозном сценарии сохрани обращение к проверяемому сервису.

## Обязательный результат и ожидаемое значение

Если сценарий обещает наличие объекта, события или строки в ответе, проверь это прямо. При проверке события перед зависимым действием останови сценарий на нарушенном предусловии. Если контракт допускает отсутствие, задай для этой ветви отдельное ожидание. Ветвления подходят для подготовки, а циклы для проверки элементов после проверки состава или количества, заданных контрактом.

Ожидаемое значение возьми из требований, эталонной записи или заранее рассчитанного примера. Например, готовые рейсы должны попасть в сводку в порядке входа. Фиксированный ответ проверяет пропуск, лишний рейс и перестановку. `if actual:` скрыл бы пустой ответ, а вычисление `expected` через тот же фильтр повторило бы ошибку в условии.

```python
def ready_trips(trips):
    return [trip_id for trip_id, status in trips if status == "ready"]


def test_summary_contains_ready_trips_in_input_order():
    trips = [(24, "ready"), (20, "held"), (17, "ready")]

    assert ready_trips(trips) == [24, 17]


def test_summary_is_empty_when_no_trips_are_ready():
    assert ready_trips([(20, "held")]) == []
```

Для первого случая подай пустой ответ или воспроизведи ошибочный фильтр в изолированной копии и убедись, что обязательная проверка падает. Второй случай подтверждает, что допустимое отсутствие явно проверено. Для события, необходимого перед записью, дополнительно проверь, что сбой предусловия оставил данные без новой записи.

## Состояние процесса в тестах

Если тест меняет переменные окружения, рабочую папку или общие настройки приложения, привяжи восстановление к области каждого изменения. Для последовательной подготовки `monkeypatch.context()` восстановит изменения и при исключении посередине блока. Восстанови прежние значения, включая отсутствие переменной. Если приложение читает настройки при импорте или кэширует их, создай новый экземпляр настроек или проверь чтение в отдельном процессе.

```python
import os
from pathlib import Path
from types import SimpleNamespace

import pytest


def load_route_config(settings):
    return os.getenv("FLEET_REGION"), Path.cwd(), settings.route


def test_failed_setup_leaves_original_config_for_next_scenario(monkeypatch, tmp_path):
    settings = SimpleNamespace(route="local")
    original_region = os.getenv("FLEET_REGION")
    original_directory = Path.cwd()

    with pytest.raises(OSError, match="broken index"):
        with monkeypatch.context() as scope:
            scope.setenv("FLEET_REGION", "west")
            scope.chdir(tmp_path)
            scope.setattr(settings, "route", "remote")
            assert load_route_config(settings) == ("west", tmp_path, "remote")
            raise OSError("broken index")

    assert load_route_config(settings) == (original_region, original_directory, "local")
```

Воспроизведи сбой после первого изменения состояния и после последующих. Проверь чтение в следующем сценарии в том же процессе. Например, замени восстановимую подмену настройки прямым присваиванием в изолированной копии и проверь, что новый сценарий увидит утечку. Изменения `env`, `cwd` и общей конфигурации видны другим потокам и задачам до восстановления. Если такие проверки идут параллельно, передавай настройки и пути экземпляру либо запускай отдельный процесс с собственными `env` и `cwd`.

## Клиенты и тестовые данные

- При частых запросах переиспользуй подключение в пределах совместимого контекста авторизации. Задай таймаут по контракту сервиса. Если запросы независимы, ограничь их параллельность доступными ресурсами. Проверь закрытие соединений при отмене и сохранение исходной ошибки. Если сервис возвращает ID запроса, приложи его к упавшему шагу для поиска в журнале.
- Если сбой зависит от случайных данных, передавай генератор в фабрику и указывай начальное значение при сбое. Повтори кейс с тем же значением и условиями запуска. Для измерений бери допустимую погрешность из требований. У идентификаторов, счётчиков и размеров проверяй точное значение, когда так задан контракт.
- Если разбор большого артефакта занимает много памяти, попробуй читать его порциями и обрабатывать записи за один проход. На одном входном файле сравни результат и пиковую память, включая неполную последнюю запись.

## Сроки и задержки

Если проверке нужна граница срока или правило задержки, передай источник времени и функцию ожидания. Для абсолютного срока используй согласованную временную шкалу, например календарное время UTC из контракта. Для длительности бери монотонные часы. В тесте подставь часы, которые продвигаются вместе с ожиданием. В примере повтор разрешён строго до дедлайна, а задержка ограничена оставшимся временем.

```python
from time import monotonic, sleep

import pytest


def wait_for_retry(deadline, *, now=monotonic, pause=sleep):
    remaining = deadline - now()
    if remaining <= 0:
        return False
    pause(min(2, remaining))
    return now() < deadline


@pytest.mark.parametrize(
    ("deadline", "allowed", "delays"),
    [
        pytest.param(43, True, [2], id="before-deadline"),
        pytest.param(41, False, [1], id="reaches-deadline"),
        pytest.param(40, False, [], id="already-expired"),
    ],
)
def test_retry_deadline(deadline, allowed, delays):
    current = 40
    requested = []

    def advance(seconds):
        nonlocal current
        requested.append(seconds)
        current += seconds

    assert wait_for_retry(deadline, now=lambda: current, pause=advance) is allowed
    assert requested == delays
```

Проверь момент точно на границе, когда замена `<` на `<=` ошибочно разрешает повтор. Подставляемое время проверяет решение клиента. Если контракт зависит от часов сервиса, планировщика или реального сетевого таймаута, проверь эту границу отдельно через соответствующий интерфейс с допуском, заданным контрактом.

## Поиск следующей правки

Сопоставь назначение команд в инструкции, конфигурации проекта и CI. Для одной обещанной быстрой проверки получи список node ID каждой командой с `--collect-only -q`, сохранив её пути, маркеры и опции. Если списки расходятся, покажи конкретный пропущенный тест и какой сбой он ловит. Более широкий ночной прогон может быть запланирован. Если отбор совпал, разное написание команд само по себе исправления не требует.

Чтобы проверить силу теста, возьми известный отказ или воспроизведи его в изолированной копии. Например, пропусти закрытие тестового ресурса и запусти выбранный сценарий, затем восстанови очистку и повтори. Зафиксируй, какая команда выявила поломку и какое утверждение сработало.

Используй имеющийся анализатор для поиска циклических импортов, повторов и сложных ветвлений. Проверь связи в исходниках, в том числе регистрацию плагинов pytest, `autouse`, косвенную параметризацию и фикстуры, запрошенные по имени. Перед удалением проверь внешние точки входа.
