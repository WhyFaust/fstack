# Проверить конкретное изменение

Зафиксируй ревизию или однозначный снимок. Для PR/MR запиши base и head,
сверь файлы с diff площадки; в Git используй `git diff <base>...<head>`.
Для патча проверь переданный снимок, включая указанные правки вне HEAD.
Для цикла по коммитам сначала запроси [план в runtime](references/cycle.md)
и передавай отчёт между раундами.

Читай первичные данные сам; правки передай владельцу. Для делегированного
ревью нужны требования, снимок и данные в свежем контексте без вердикта.
Сообщи координатору об истории автора, нехватке доступа и смене снимка.
Применяй [$fstack:verify](../verify/SKILL.md) к доказательствам и
[$fstack:principles](../principles/SKILL.md) к существенному вопросу о границе,
модели или состоянии.

## Проверить изменённое поведение

1. Прочитай поручение, правила, diff, окружающий код и потребителей.
   Бери правила PR/MR и `REVIEW.md` из подтверждённой целевой ревизии.
   Для прав, установки, выпуска и формата данных проверь реального
   потребителя и запроси независимое подтверждение спорного существенного замечания.
2. Сверь решение с исходной целью. Для исправления найди изменённое
   условие сбоя и доказательство. Проверь, нужны ли новые слои, настройки
   и состояния потребителям или обслуживают оставшийся дефект. Временное
   смягчение оценивай в порученных границах без зачёта устранения причины. Не требуй перестройки без
   достижимого нарушения или подтверждённой лишней сложности.
3. Проверь достижимые изменения поведения, совместимость, ресурсы,
   конкуренцию, ошибки и тесты. Для существенной границы доверия или порученного
   ревью безопасности проследи субъект, права, вход, проверку доступа и операцию.
   Покажи влияние diff на путь или последствия. Усиление рабочей защиты
   обозначь как совет. Недоверенный код запускай только изолированно: без сети,
   секретов и общих ресурсов, с правами и лимитами; иначе читай. Существенные
   последствия вне diff проверь по [$fstack:impact](../impact/SKILL.md).
4. Для замечания укажи вход, условия и нарушенный контракт. По возможности
   воспроизведи отказ в разрешённых изолированных ресурсах, запиши ожидаемое
   и фактическое. Иначе покажи достижимый сценарий и механизм статически,
   объясни отсутствие запуска. Недоказанный путь — гипотеза. Для старой
   причины проверь новую достижимость, последствия или нарушение критерия.
5. Сверь тесты с требованиями. Сопоставь заявленную причину, diff и исходный
   сценарий: скрытая ошибка, обход входа или ослабленная проверка не доказывают
   исправление даже при зелёном CI. При нехватке данных отметь пробел.
   Для Python-тестов примени [$fstack:python](../python/SKILL.md) к структуре
   и assertions. Для настройки или генерации проверь объект и потребителя.
6. В следующем раунде проверь правки, открытые замечания и их потребителей.
   При расширении риска повтори полный проход; при `owner` верни нерешённое
   владельцу для пересмотра.

## Сформулировать замечание

Объедини проявления одной причины. Для дефекта дай приоритет, место, сценарий,
нарушение, доказательство и минимальную коррекцию. Отдели советы и стиль,
включая [$fstack:no-comments](../no-comments/SKILL.md). Вердикт может быть
без замечаний; в любом случае дай ревизию, проверки и пробелы.

Если готовность зависит от CI, передай в [`check`](references/cycle.md#проверить-готовность)
имена обязательных проверок из правил проекта и последние попытки для данного
head из доверенного CI. Ревью не разрешает слияние, публикацию или развёртывание.
