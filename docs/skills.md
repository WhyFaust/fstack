# Каталог навыков

По умолчанию методы fstack не выбираются автоматически. Полный процесс
включается через `/faust-mode`; отдельный метод можно вызвать явно.

Один навык отвечает за один понятный результат. Выбирай основной метод по
текущей задаче, затем добавляй только нужный предметный приём. Полный каталог
не загружается как обязательная последовательность.
Все навыки следуют [единому шаблону](../skills/adapt-skill/references/template.md):
вход и границы, порядок работы, проверка и результат. Предметные шаги различаются;
при создании и доработке форму поддерживает `adapt-skill`.

## Короткий playbook

Перед изменением выбери доказательство по `verify-result`. При существенных
зависимостях добавь `plan-work`. Координатор ведёт задачу через `delegate-work`,
назначает владельцев и может сразу поручить известное исправление агенту
с правом записи. Исследование может завершиться ответом. Для проверки подходит
независимый результат CI, покрывающий критерий на актуальной ревизии.
`review-change` нужен по требованию проекта или пользователя либо для
конкретного открытого вопроса о коде. [Выбор исполнителя](orchestration.md#от-поручения-к-приёмке).

| Запрос | Рабочий маршрут | Условие приёмки |
| --- | --- | --- |
| Объяснить код | `investigate-code`; `trace-history`, если нужен мотив решения | Ответ связан с текущим кодом или историческим источником |
| Прочитать присланную статью или выполнить поручение по ней | `deepread`; при необходимости добавь метод выполнения поручения | Результат сохраняет существенные данные, условия и связь с источником |
| Найти, что улучшить и с чего начать | `improve-codebase` | Приоритеты обоснованы текущим кодом |
| Подготовить или актуализировать план выбранного улучшения | `plan-improvement` | План исполним на указанном снимке без контекста чата |
| Добавить возможность | `implement-change`; `design-change` при неясном контракте | Основной сценарий и важный отказ проверены у потребителя |
| Исправить сбой | `debug-failure` | Исходный сбой устранён; предел воспроизведения назван |
| Упростить существующий код | `refactor-code`; `simplify-change` только для готового diff | Сохранение поведения подтверждено |
| Изменить общий контракт | `assess-impact`, затем основной метод; `migrate-contract` при переходе | Учтены потребители, старые данные и отказ перехода |
| Проверить свойство автомата подсистемы | `model-check-state` | Прогон связан с моделью и кодом, выбранная трасса показана в Mermaid |
| Проверить результат | `verify-result` для доказательств, `verify-project` для прогона, `review-change` для вопроса по diff | Независимые выводы относятся к одному снимку |
| Повторять проверку проекта | `prepare-verification`; позже `maintain-verification` | Пользовательские пути связаны с командами и признаками успеха, доказательства доступны после очистки |
| Продолжить или завершить работу | `resume-task` / `checkpoint-task`; `use-memory` для подключённого проекта | Состояние сверено, устойчивые выводы отделены от журнала задачи |

Нужный предметный метод открывай напрямую. `engineering-principles` помогает
выбрать его при неясном риске, но не является обязательной промежуточной загрузкой.
Глубина проверок и остановка зависимых этапов описаны в
[verify-result](../skills/verify-result/SKILL.md#выбрать-глубину-по-риску).

## Правила выбора

Координатор выбирает штатного агента Codex и передаёт ограниченное поручение через delegate-work.
Исполнитель выбирает по метаданным нужный метод и справки; select-skills помогает
при выборе маршрута. К однозначному методу переходят напрямую с предметными
дополнениями текущего этапа. Простой ответ из имеющихся данных допускает маршрут
без навыков. Исполнитель кратко указывает, какие навыки повлияли на работу и как.
Полный каталог и тексты навыков в главный контекст не копируются. Запуск подагентов описан в [оркестрации](orchestration.md).

assess-impact применяют при исследовании или планировании, если есть существенный
риск для потребителей общего контракта. Если поручена реализация, оценку
завершают до её начала. simplify-change убирает сложность только
подготовленного изменения, refactor-code решает самостоятельную задачу
перестройки существующей реализации.
Смена основного результата меняет метод; предметные методы не начинают новую
оркестрацию и не расширяют полномочия.

design-change разрешает инженерную неопределённость, design-ui прорабатывает
сценарий и визуальное решение, playwright-cli управляет браузером.
verify-result определяет силу и пригодность доказательства. verify-project
проверяет реальную границу, при необходимости восстанавливая минимальный путь
существующими средствами. prepare-verification сохраняет передаваемую инструкцию,
maintain-verification обновляет её; разовый запуск не требует их цепочки.
Для нескольких путей инструкция связывает названия из интерфейса с командами и
ожидаемым поведением. При приёмке видимого изменения verify-project сохраняет
снимок проверенного состояния или запись значимого перехода.
`watch-pr` читает состояние, `resolve-review` разбирает замечания, `ship-pr`
выполняет слияние в пределах поручения. Задача на изменение с публикацией
через GitLab MR в активном режиме включает [цикл до подтверждённого слияния](orchestration.md#от-draft-mr-до-слияния-в-gitlab).
Для разового запроса статуса достаточно `watch-pr`. Навык `glab` нужен при
переходе с GitLab MCP на CLI.

В установленном плагине можно вызвать `$fstack:debug-failure` или другой
метод по его имени. UI-подсказка использует то же полное имя `$fstack:debug-failure`,
которое возвращает фактический каталог клиента. Одноимённые личные копии следует убрать из обнаружения
после проверки установленного пакета; чужие плагины не меняй.

Внутри включённого faust-mode исполнитель выбирает метод по смыслу поручения.
При выключенном режиме доступен прямой вызов конкретного метода, например
`$fstack:review-change`, без включения координатора. Аудит нужен для поиска и приоритизации улучшений,
а не как обязательный этап каждого исправления. codex-config-evaluation
вызывается явно: сравнение моделей и конфигураций требует отдельного поручения.
Настройка, запись, публикация и делегирование всегда ограничены текущей задачей.

При изменении кода применяется no-comments. Для Python основной навык python
дополняется только нужными справками: типизация, asyncio, автотесты или их ресурсы.
Диагностика зависаний и профилей процесса описана в справке debug-failure.
Для подтверждённой поправки implement-change и debug-failure помогают выбрать
[защиту от повторения](../skills/implement-change/references/prevent-repeat.md)
в интерфейсе или штатных проверках проекта.
