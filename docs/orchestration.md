# Где находятся инструкции fstack

| Слой | Источник | Когда используется |
| --- | --- | --- |
| Глобальный профиль | [profile/AGENTS.md](../profile/AGENTS.md) | Краткие правила координатора. Helper копирует текст в управляемый блок глобального `AGENTS.md`, сохраняя пользовательский текст вокруг блока. |
| Проект | [AGENTS.md](../AGENTS.md) | Правила разработки самого fstack, включая контракты пакета и команды проверки. |
| Рабочий протокол | [fstack:delegate-work](../skills/delegate-work/SKILL.md) | Координатор открывает навык перед делегированием. Здесь описаны назначение ролей, связь исполнителей, ожидание событий и приёмка. |
| Роли | [profile/agents/](../profile/agents/) и [контракт профиля](codex.md#модель-и-reasoning) | TOML задают обязанности, модель и reasoning исполнителей. Helper устанавливает роли вместе с профилем. |

Codex читает глобальные инструкции при старте, затем добавляет по одному
файлу инструкций на каталог от корня проекта до рабочего каталога. Вложенный
`AGENTS.md` применяется при обнаружении по этому пути. Ссылка на файл сама по
себе его не загружает. Обычные Markdown-файлы открываются по необходимости.
[Правила обнаружения AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

Протокол использует встроенные возможности Codex. Лимит потоков, способы
ожидания и доступность прямых сообщений между исполнителями зависят от клиента.
[Документация Codex о подагентах](https://learn.chatgpt.com/docs/agent-configuration/subagents)

Нативный runtime и его проверки находятся в `tools/fstack/`. Навыки вызывают
готовый `bin/fstack` из установленного пакета; команды разработки описаны
в [справке](development.md#минимальные-проверки).
[Руководство Codex по созданию навыков](https://learn.chatgpt.com/docs/build-skills)

## От поручения к приёмке

Координатор задаёт результат, наблюдаемые критерии, снимок, разрешённые действия
и владельца. Исполнитель выбирает метод по [playbook](skills.md#короткий-playbook)
и передаёт проверяемый артефакт. Для существенного изменения reviewer оценивает
сам diff, verifier сверяет доказательства с критериями. Только после разрешения
существенных замечаний координатор принимает результат текущего снимка.

Порог проверок определяет [риск](../skills/verify-result/SKILL.md#выбрать-глубину-по-риску),
а не модель, число файлов или уверенность автора. Повторный отказ требует
установить причину и изменить вход или план, а не запускать тот же запрос снова.
Поля модели и effort остаются в TOML ролей; протокол не переопределяет их.

Запрет reviewer менять код является инструкцией, а не ограничением инструментов.
Реальные права чтения задаёт среда, если она поддерживает такую изоляцию.
Без неё нужно соблюдать запрет и сверять неизменность снимка после ревью;
называть такую роль технически read-only нельзя.
