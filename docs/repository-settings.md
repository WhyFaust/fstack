# Настройки GitHub вне файлов пакета

PR меняет код и workflow. Правила защиты ветки включаются отдельно в настройках
GitHub администратором; файл в репозитории не активирует их сам по себе.

## Проверяемый контракт

| Параметр | Требование |
| --- | --- |
| Рабочая ветка | Изменения через отдельные ветки и PR |
| Проверки PR | Все jobs `package` из актуальной матрицы [workflow](../.github/workflows/release.yml) для текущего head/merge snapshot |
| История main | Без force-push и удаления |
| Метод слияния | Итоговый Conventional Commit, предпочтительно squash |
| Workflow token | contents: read для проверок; contents: write только для release |
| Релиз | Проверенный github.sha; восстановление только точного производного коммита версии; обычный push |

При настройке required checks копируй точные имена jobs из последнего прогона
workflow. После изменения матрицы сверяй этот список: прежнее имя проверки
не получает статус от нового job и может заблокировать слияние.

## Совместимость защиты с релизом

Текущий механизм добавляет в main коммит согласованных версий от workflow.
Поэтому нельзя включить обязательный PR или required status checks для каждого
нового коммита main, одновременно запретив эту запись: новый коммит версии
ещё не имеет собственных статусов матрицы, и выпуск остановится.

Перед введением обязательных проверок main выбери и проверь один вариант:
отдельная авторизованная release identity с узким разрешением на служебный
коммит либо отдельный процесс release PR. Не назначай широкий bypass людям
или боту без необходимости, не отключай защиту из скрипта и не добавляй PAT
в исходники. GITHUB_TOKEN не следует считать автоматически имеющим bypass.

При командном использовании предпочтителен процесс release PR; его введение
меняет цикл выпуска и настройки доступа и требует отдельной проверки на GitHub.
До такой настройки checks в PR дают доказательства, но не серверный запрет
прямого push. Не сообщай пользователю, что защита включена, только по наличию CI.
