# Профиль Codex: конфигурация, инструкции и роли

fstack поставляет навыки, роли исполнителей и правила главного координатора.
После установки плагина запусти **Setup** или попроси `$fstack:fstack-setup`
настроить полный профиль. Агент синхронизирует роли и инструкции, согласует
необходимые настройки и проверит результат в том же ходе. Полный порядок
работы и выбор моделей описаны в [руководстве оркестрации](orchestration.md).

## Что где находится

| Слой | Источник fstack | Назначение |
| --- | --- | --- |
| Настройки клиента | [config.example.toml](../profile/config.example.toml) | Исходные значения для точечного согласования конфигурации через Setup |
| Правила координатора | [AGENTS.md](../profile/AGENTS.md) | Канонический источник управляемого блока в глобальном `AGENTS.md` |
| Роли | [profile/agents/](../profile/agents/) | Пять TOML для устойчивого каталога `CODEX_HOME/agents/` |
| Методы работы | [каталог навыков](skills.md) | Навыки установленного плагина, имена `fstack:...` |

`CODEX_HOME` по умолчанию — `~/.codex`. Для отдельного профиля задай переменную
среды или передай `--home` helper. Каталог `profile/` внутри плагина является
источником конфигурации, инструкций и ролей; он сам не становится глобальным профилем.

## Что Codex подключает нативно

Навыки загружаются из установленного плагина. В манифесте fstack уже задан
`extensions.com.openai.onboardingSkill = "./skills/fstack-setup/SKILL.md"`.
Нативный Setup запускает этот навык после установки — в новой беседе либо
в той, где плагин был установлен. Это действие пользователя, а не автоматический
install hook; см. [Add an onboarding skill](https://developers.openai.com/plugins/build/plugins#add-an-onboarding-skill).

Роли Codex обнаруживаются в `CODEX_HOME/agents/` или проектном `.codex/agents/`.
В проверенной [схеме компонентов плагина](https://github.com/openai/codex/blob/695961ee88a2c84c0919814a4345b94a2d10f3ca/codex-rs/plugin/src/manifest.rs#L18-L24)
нет компонента для ролей или `AGENTS.md`; [загрузчик ролей](https://github.com/openai/codex/blob/695961ee88a2c84c0919814a4345b94a2d10f3ca/codex-rs/agent-roles/src/loader.rs#L23-L88)
читает активные слои конфигурации. Поэтому Setup переносит управляемую часть
профиля в поддерживаемые каталоги. Само наличие `profile/` в пакете её не активирует.

## Настройка из интерфейса

Манифест fstack объявляет стартовые запросы для трёх действий; их отображение
зависит от клиента. Запусти **Setup** у плагина или, если он недоступен,
вызови `$fstack:fstack-setup` с нужным действием:

| Действие | Пример запроса | Что меняется |
| --- | --- | --- |
| Полный профиль | «Настрой полный профиль fstack с сохранением моих настроек» | Роли, управляемый блок инструкций и необходимые настройки |
| Выбранные настройки | «Покажи настройки и помоги изменить reasoning и параллельность» | Только выбранные поля конфигурации |
| Проверка | «Проверь профиль fstack без изменения файлов» | Ничего; агент возвращает текущие значения и ограничения проверки |

Это диалог с навыком. В проверенном публичном
[формате интерфейса плагина](https://github.com/openai/codex/blob/695961ee88a2c84c0919814a4345b94a2d10f3ca/codex-rs/plugin/src/manifest.rs#L40-L58)
нет произвольной формы настроек, которую fstack мог бы объявить в манифесте.
Агент показывает действующие значения и уточняет только неизвестные желаемые
параметры. Короткие карточки выбора используются, если `request_user_input`
действительно доступен; иначе достаточно обычного ответа в беседе. Для этого
не нужны экспериментальные флаги. Обычный полный Setup проходит без анкеты:
он сохраняет действующие предпочтения и дополняет поддерживаемые пробелы.

Setup показывает эффективные настройки и сохраняет пользовательские изменения.
Модель и effort исполнителей определяются TOML ролей; см.
[контракт профиля](#модель-и-reasoning). Запрос изменить выбранную настройку
затрагивает только определяющие её поля. Изменение параметров конфигурации
не запускает синхронизацию инструкций координатора. Проверка без изменений
не создаёт запись или резервную копию.

Эти параметры относятся к глобальному профилю Codex в выбранном `CODEX_HOME`
и могут влиять на другие его чаты. Они не изолированы внутри fstack.
[Переключатель модели текущего чата](https://learn.chatgpt.com/docs/models)
и сохранённые настройки по умолчанию — отдельные уровни. Агент сообщает
эффективные значения и необходимость новой сессии. Порядок диалога описан
в [справке настройки](../skills/fstack-setup/references/settings-ui.md).

## Как Setup согласует config.toml

Агент проверяет действующие слои конфигурации, доступные модели и уровни reasoning.
Существующие предпочтения, лимиты, авторизация, провайдеры и настройки других
плагинов сохраняются. При обычной установке добавляются отсутствующие применимые
значения. Явно выбранное пользователем значение заменяет прежнее в той же области;
`approval_policy` и `sandbox_mode` ради установки fstack не меняются.
Пример предлагает значения для нового профиля; существующий `config.toml`
не заменяется целиком. Настройки ролей устанавливаются вместе с их TOML.
Скрипт `sync_profile.py` этот файл не записывает: точечную правку выполняет
Setup-агент по [справке конфигурации](../skills/fstack-setup/references/configuration.md).

Записи marketplace и `[plugins."fstack@fstack"]` создаёт `codex plugin add`.
Не подменяй их путём к определённой версии кэша и не дублируй навыки в `skills/`.
Notion и другие провайдеры устанавливаются своими плагинами; их настройки
и авторизация не входят в этот пример. Для личных ролей отдельные
секции `[agents.<name>]` с `config_file` не нужны: клиент обнаруживает standalone TOML.

## Модель и reasoning

| Роль | Модель | Reasoning |
| --- | --- | --- |
| `auditor` | `gpt-6.1-sol` | `low` |
| `coder` | `gpt-6.1-sol` | `medium` |
| `reviewer` | `gpt-6.1-sol` | `high` |
| `verifier` | `gpt-6.1-sol` | `low` |
| `allure_analyst` | `gpt-6.1-sol` | `medium` |

Источники значений: [TOML ролей](../profile/agents/).
[Пример конфигурации](../profile/config.example.toml) предлагает координатору
`gpt-6.1-sol` / `low`, исполнителям без настроек роли ту же модель / `medium`
и лимит двух дочерних потоков. Это выбранная политика, без модельного бенчмарка.

[Codex применяет](https://learn.chatgpt.com/docs/agent-configuration/subagents)
настройки в порядке: поля TOML роли, параметры запуска, значения `[agents]`,
наследование родителя. Поэтому передача другого effort или модели через
`spawn_agent` не перекрывает заполненные поля роли. Координатор согласует
параметры поручения с ролью. Явно запрошенное изменение роли требует правки
её TOML в целевом профиле; обычная фраза в поручении его не выполняет.

Полный Setup устанавливает эти значения вместе с ролями. Неизменённые
управляемые файлы обновляются; личные изменения вызывают конфликт helper.
Сначала покажи пользователю конкретную замену и разреши конфликт, сохраняя
его настройки. Для переноса нового выбора между установками меняется источник
`profile/agents/`; установленный кэш не редактируется.

Поддержку выбранной модели и effort проверяй в клиенте перед запуском.
Недоступность не разрешает автоматическую подмену модели. Разбор TOML
и strict config не подтверждают доступность модели или исполнение роли.
Авторизация, провайдеры и действующие ограничения среды сохраняются.

## Какой AGENTS.md использовать

[profile/AGENTS.md](../profile/AGENTS.md) — единственный источник управляемых
правил координатора. Helper помещает его содержимое между маркерами fstack
в глобальном `CODEX_HOME/AGENTS.md`, сохраняя текст вне блока. Отдельного
`profile/links.md` и расширенного шаблона для ручного копирования больше нет.

Главный агент хранит цель, ограничения, решения и состояние поручений, принимает
краткие результаты со ссылками на доказательства. Полный diff читает `reviewer`,
первичные логи и результаты проверок — `verifier`. Исполнители сами выбирают
методы через `fstack:select-skills`; их подробная работа остаётся в их контексте
и артефактах. Правила приёмки приведены в [руководстве оркестрации](orchestration.md).

В проектном `AGENTS.md` указывай сведения конкретного репозитория: команды,
поддерживаемые версии, контракты, локальную среду и ограничения общих ресурсов.
Не дублируй там глобальный блок или все тексты навыков.

[Обнаружение инструкций](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
начинается с `AGENTS.override.md` либо `AGENTS.md` в `CODEX_HOME`, затем добавляет
файлы от корня проекта к рабочему каталогу. Ближайшие инструкции уточняют предыдущие;
на одном уровне `AGENTS.override.md` выбирается раньше `AGENTS.md`.
Если глобальный override активен, управляемый блок в обычном `AGENTS.md` может
не попасть в контекст. Helper не изменяет override. Setup проверяет этот случай,
готовит конкретную правку с сохранением авторских правил и запрашивает решение
только для неразрешённой замены. До разрешения такого конфликта профиль настроен частично.

## Роли

| Роль | Назначение |
| --- | --- |
| `auditor` | Ограниченное исследование и аудит без правок |
| `coder` | Реализация, исправление и рефакторинг на языке проекта, включая Python |
| `reviewer` | Независимая проверка определённой ревизии |
| `verifier` | Проверки, CI и первичные артефакты без исправления проверяемого кода |
| `allure_analyst` | Allure, попытки, группы отказов и решающие вложения |

Codex обнаруживает личные standalone TOML в `CODEX_HOME/agents/`, а проектные —
в `.codex/agents/`; см. [официальное руководство](https://learn.chatgpt.com/docs/agent-configuration/subagents).
Автоматическое подключение ролей из манифеста плагина здесь не используется.
Выбирай исполнителя по поручению; роли не создают собственных подагентов.
Для независимого ревью основной агент должен назначить свежий контекст,
например `fork_turns="none"`, когда это поддерживает инструмент.

Роли ссылаются на навыки fstack и применимые провайдеры из текущего каталога.
Allure Analysis, KISHKI, Notion, RTK и OpenAI Docs не копируются в fstack
и не устанавливаются helper. Notion предоставляет общую память через отдельный
MCP; RTK сокращает шум. См. [интеграции](integrations.md). Отсутствие нужного провайдера обозначается в той задаче,
где он нужен, а не маскируется несуществующим инструментом.

## Установка и первое принятие

Установи плагин способом из [руководства установки](installation.md).
Затем выбери **Setup** в интерфейсе плагина или вызови `$fstack:fstack-setup`
с просьбой настроить полный профиль. Такой запрос разрешает обычную настройку:
агент показывает краткий план, применяет его и проверяет итог без повторного
общего вопроса о разрешении. Запрос только проверки остаётся без изменений.

Setup сам определяет целевой `CODEX_HOME` и установленный источник по пути
текущего навыка либо `installedPath`, проверяет Python 3.11+ и конфликты.
После синхронизации он согласует конфигурацию, повторяет dry-run и проверяет
TOML, эффективные настройки и обнаружение доступными средствами клиента.
Вручную копировать роли, инструкции или пример конфигурации не требуется.

Решение пользователя нужно при конкретной неразрешённой замене: например,
конфликтующей личной роли или override, скрывающем новые правила. Агент показывает
затронутые файлы и подготовленное исправление. Неразрешённый конфликт, выключенные
агенты или недоступная проверка отражаются в итоговом статусе.

### Резервный вариант: прямой запуск helper

Если предпочитаешь выполнить синхронизацию вручную, в PowerShell сохрани путь,
возвращённый клиентом, и сначала посмотри план. Эти команды управляют ролями
и блоком инструкций; согласование `config.toml` выполняет Setup.

```powershell
$installedPlugin = codex plugin add fstack@fstack --json | ConvertFrom-Json
$profileSync = Join-Path $installedPlugin.installedPath 'scripts/sync_profile.py'
python $profileSync
python $profileSync --apply
```

Для helper нужен Python 3.11+; сторонних Python-пакетов ему не требуется.
`--home` выбирает целевой профиль вместо `CODEX_HOME` и значения по умолчанию.
Dry-run не создаёт файлов и не разрешает выполнение пробных агентных задач.

Если существующие роли отличаются от пакета и ещё не управляются fstack, обычный
запуск покажет конфликт. Сначала сравни файлы. Для осознанного первого принятия:

```powershell
python $profileSync --apply --adopt
```

Флаг `--adopt` работает только с `--apply`. Изменённая или отсутствующая уже
управляемая роль остаётся конфликтом и с этим флагом. Все конфликты проверяются
до записи; при конфликте отдельные независимые роли не обновляются. Перед изменениями
создаётся резервная копия в `CODEX_HOME/fstack/backups/`, состояние хранится в `fstack/profile.json`.
На POSIX новая копия закрыта правами 0700/0600. На Windows новый каталог
получает закрытую DACL для текущего пользователя и SYSTEM до записи данных;
ошибка настройки прав прерывает обновление. Старые резервные копии не меняются:
при обновлении проверь их доступ отдельно, особенно в общем CODEX_HOME.
Существующий глобальный `AGENTS.md` сохраняется, кроме собственного блока fstack.

## Обновление и восстановление

После установки новой версии плагина снова запусти **Setup** или
`$fstack:fstack-setup` с запросом обновить полный профиль. Агент берёт источник
из текущей установленной версии и выполняет тот же порядок настройки и проверки.
Для прямого запуска helper заново получи `installedPath`; старый каталог версии не используй.
Повтор без изменений возвращает `unchanged` и не создаёт новую резервную копию.
Если в исходниках пакета изменилась роль, а локальная копия сохранила управляемый
хеш, helper обновит её и сохранит предыдущую. Ручная правка управляемого файла
или блока останавливает синхронизацию; сначала согласуй её с исходниками пакета.

### Миграция набора ролей

Состояние `fstack/profile.json` сохраняет `schema: 1`. Helper принимает только
точный прежний набор управляемых ролей с `python_coder` либо новый набор с
`verifier`; произвольный состав состояния отклоняется. Python-задачи теперь
выполняет `coder` с навыком `fstack:python`.

| Состояние прежнего `agents/python_coder.toml` | Действие helper |
| --- | --- |
| Файл принадлежит fstack и совпадает с сохранённым хешем | Сохраняет приватную копию и удаляет роль |
| Управляемый файл изменён или отсутствует | Останавливается с конфликтом, в том числе при `--adopt` |
| Файл существует, но не принадлежит состоянию fstack | Сохраняет его и сообщает в `unmanaged_retired` |

В JSON-результате `changes` перечисляет все затронутые пути, `removed` — удаления:
запланированные в dry-run и выполненные при `--apply`. Поле `unmanaged_retired`
содержит сохранённые неуправляемые копии снятой роли. Проверь такие копии и при
необходимости перенеси их вне путей обнаружения ролей. `--adopt` их не удаляет.

### Восстановление

Резервная копия содержит прежние файлы и списки созданных и удалённых путей.
При ошибке helper откатывает собственные изменения. Если после удаления роли
другой процесс заново создал её файл, откат сохраняет эту запись и сообщает
об ошибке восстановления; дальнейшее согласование выполняется из резервной копии.
При ручном восстановлении согласуй роли, управляемый блок и `fstack/profile.json`
как одно состояние; не подменяй только хеш для подавления конфликта.
Наличие `fstack/profile.lock`
означает занятую или прерванную синхронизацию. До ручного удаления lock убедись,
что указанный в нём процесс больше не выполняется.

## Удаление и применение настроек

`codex plugin remove fstack@fstack` удаляет запись плагина из конфигурации Codex
и его кэш. Отдельно синхронизированный профиль — роли, блок `AGENTS.md` и состояние
fstack — остаётся на месте. Нативное удаление плагина не вызывает очистку этих
файлов; это видно в [uninstall_plugin_id](https://github.com/openai/codex/blob/695961ee88a2c84c0919814a4345b94a2d10f3ca/codex-rs/core-plugins/src/manager.rs#L2485-L2515).
Для полного удаления профиля требуется отдельное поручение с проверкой его
управляемых файлов и сохранением пользовательских изменений.

После удаления плагина навыки, на которые ссылаются роли, недоступны. Восстанови
плагин либо отдельно согласуй оставшийся профиль. После установки или обновления
профиля начни новую сессию: чтение TOML и обнаружение файлов не доказывают
исполнение роли, а изменение настроек не переключает текущую модель.
