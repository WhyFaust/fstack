# Память проекта

## Подключение

Открой существующий vault Obsidian и одобри хуки fstack в настройках Codex.
Начни обычный чат в рабочей папке. Хук найдёт vault и создаст область проекта.
Git worktree одного репозитория используют общую область. Если папка уже была
подключена к памяти, обычный `git init` сохраняет её привязку. Если vault несколько,
выбери рабочий через `memory vault --set PATH`. Для ручного подключения,
восстановления отключённой памяти или выбора имени используй
`memory init --vault PATH --repo PATH --project NAME --mode auto`.

Команды `memory` вызываются через запускатель из установленного пакета.
Запускай их из рабочей папки проекта. В следующих командах укажи
абсолютный путь своего запускателя.

```bash
/bin/sh "$FSTACK_ROOT/launchers/fstack.sh" memory status
```

```powershell
& "$env:FSTACK_ROOT/launchers/fstack.ps1" memory status
```

Убедись, что `status` показывает нужный проект и vault. Сообщи в чате
долговечное правило, затем проверь его применение в новом чате того же проекта.
В Obsidian записи доступны через `Codex Memory/Home.md`. Для ручной проверки
используй `memory search "запрос"` и `memory show ID`.

## Запись и поиск

В режиме `auto` подтверждённые решения и поправки попадают в записи проекта.
Кандидаты для проверки остаются в Inbox. Режим `inbox` отправляет на ручную
проверку все новые записи. Предпочтение становится доступным другим проектам
того же vault по явному указанию пользователя.

Хуки связывают операцию с конкретным ходом. Главный агент готовит её,
`PostToolUse` принимает, а `Stop` или `SubagentStop` применяет. В Plan запись
пропускается. Прерывание хода отменяет его очередь. После сбоя хранилища
неотменённая операция может примениться в следующем обычном ходе того же чата.
Если заметки нет, проверь доверие к хукам, `memory status` и `memory diagnostics`:
`{"staged": true}` означает, что команда проверила аргументы и токен.
`phase: stage` показывает, что хук принял операцию, а `phase: applied` означает,
что `Stop` её применил. При `--skip` новой заметки не будет. В PowerShell пути
из подсказки можно заключать в одинарные или двойные кавычки; используй точные
пути и запускай команду отдельно.
[Работа агента с памятью](../skills/memory/SKILL.md).

В новом чате и при запуске подагента хук передаёт инструкцию поиска по памяти
проекта. Для большого хранилища поиск запускается отдельной командой в ходе,
чтобы успело выполниться само событие ввода.

В локальном Codex Desktop `Stop` запрашивает итог хода, запущенного через
`create_thread`, `send_message_to_thread` или сообщением от подагента.
У нативного подагента итог запрашивает `SubagentStop`. `PostToolUse` принимает
`memory report`, после чего завершение сохраняет одно новое решение с источником.
Режим хода берётся из журнала клиента. Для записи нужны обычный режим,
подтверждённое происхождение хода и область проекта. Режим проекта `auto`
сохраняет решение, `inbox` ставит его на проверку. [Порядок записи](../skills/memory/SKILL.md#итог-поручения-codex).

## Заметки и представления Obsidian

В записи можно редактировать текст и добавлять стандартные свойства `tags`,
`aliases`, `cssclasses`: строкой или списком строк YAML. Подтверждение сохраняет их исходное оформление. Эти свойства не меняют область, статус и
цепочку замен, не становятся новыми правилами для агента. Служебные поля и имя
файла с ID изменяет runtime. Для внутренней ссылки укажи путь заметки и подпись
`[[путь/заметки|Название]]`, для источника вне vault используй обычную Markdown-ссылку.

В таблице есть источник решения и ссылка на заменённую версию. Inbox начинается
со старых кандидатов, история с новых подтверждений. Представление "Сохранённые" включает заменённые записи. `memory search`, `show` и `history`
учитывают также замены, оставшиеся в отметках об удалении.
Если тело заметки слишком длинное или повреждена его кодировка, поиск и Inbox
пропускают заметку с читаемыми служебными полями. Связь с предыдущей версией
сохраняется. Команда `show` для такой заметки сообщает ошибку, чтобы её можно
было исправить в Obsidian.

Копия таблицы создаётся при её отсутствии. Существующие представления и фильтры сохраняются.
Встроенные представления на странице проекта отфильтрованы по её области;
прямое открытие Library.base показывает все проекты и общие предпочтения.

Для проверки оформления нужен открытый Obsidian; сам runtime работает без него.
При наличии штатного CLI сначала вызови `obsidian help`, затем укажи vault первым
параметром. Не устанавливай сторонний npm-пакет с похожим именем.

```text
obsidian vault="Проверочный vault" base:query path="Codex Memory/Library.base" view="Сохранённые" format=paths
obsidian vault="Проверочный vault" backlinks path="Codex Memory/Projects/pilot/pilot.md" format=json
```

Сверь вывод с ожидаемыми записями, а не только код завершения. Открой Home, страницу
проекта, её Inbox и историю; перейди по изменённой ссылке. Прямой запрос к базе
не проверяет фильтр встроенного представления.

## Несколько устройств и отключение

Синхронизируй папку `Codex Memory` в Obsidian, включая Markdown, JSON, Bases и
Canvas. В Obsidian Sync на каждом устройстве включи "Sync all other types"
и перезапусти Obsidian, чтобы передавались файлы JSON с отметками об удалении.
[Настройки Obsidian Sync](https://obsidian.md/help/sync/settings).

После синхронизации выполни `memory init` на каждом устройстве с его путями
и тем же именем проекта. Привязки и очередь операций локальны. Перед изменением
или удалением записи с другого устройства дождись доставки предыдущих правок.

`memory disable` выключает автоподключение проекта на данном устройстве до
следующего явного `init`.
