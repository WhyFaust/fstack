# Примеры работы

## Улучшать кодовую базу автотестов

```text
$fstack:audit Изучи весь проект автотестов. Предложи улучшения и реши по каждому, стоит ли делать его сейчас.
```

В примере с журналом два локальных теста проходят, даже если после закрытия
остаётся блокировка. В выборке для CI есть третий тест, который открывает
журнал во второй раз. Должен ли этот сценарий входить в быстрый запуск
каждого разработчика? Если да, агент
предложит использовать маркер `quick` и для локального запуска. Если нужен
отдельный интеграционный прогон, стоит сохранить два набора и назвать, что
проверяет каждый. Можно принять порядок работы или выбрать пункты по ID.

```text
$fstack:audit Вернись к списку из прошлого разбора: <ссылка>. Проверь, что уже исправлено и изменились ли основания для отложенных пунктов.
```

[Навык audit](../skills/audit/SKILL.md) · [Приёмы для автотестов](../skills/python/references/aqa.md)

## Повторить аудит блокировки

Нужен Python с установленным pytest. Из корня fstack перейди в `docs/examples/receipt`.
Флаг `--keep-lock` воспроизводит поломку на временном файле. Выполняй команды
по отдельности. Они соответствуют двум выборкам на схеме в README.

| Команда | Что увидишь |
| --- | --- |
| `python -m pytest -q tests/unit --keep-lock` | 2 прошли. Эти тесты не открывают тот же журнал повторно. |
| `python -m pytest -q -m quick --keep-lock` | 2 прошли, 1 упал. Вторая попытка открытия завершается с `FileExistsError`. |
| `python -m pytest -q tests/unit` | 2 прошли с обычной очисткой. |
| `python -m pytest -q -m quick` | 3 прошли. Второй сеанс читает запись первого. |

Чтобы найти разницу до запуска тестов, добавь к обеим командам
`--collect-only` и сравни имена собранных сценариев.
[Открытие журнала](examples/receipt/receipt_journal.py) · [Проверка двух сеансов](examples/receipt/tests/integration/case_shifts.py)

## Проверить перенос метода

```text
$fstack:skill Адаптируй этот приём к нашей проверке очереди. Покажи, что произойдёт при повторной доставке и что изменится, если первая попытка не дошла до записи.
```

В результате видно, какое действие выбрал агент в каждом случае, что сохранилось
после повтора и чем это проверено. [Перенос рабочего метода](../skills/skill/SKILL.md#перенести-рабочий-метод).

## Сбой или медленная джоба

```text
/faust-mode Разберись, почему публикация отчёта занимает несколько часов.
Лог: <путь>. Исходники: <ревизия>. Покажи, где уходит время и как проверить исправление.
```

Если нужно довести исправление до ревью, добавь: «Открой MR, дождись обязательных
проверок для его текущего SHA и оставь открытым».

## Продолжение плана с несколькими границами

```text
/faust-mode Продолжи план из MR. Следующий шаг — API для атомарного создания
группы записей. Проверь повтор запроса и чтение старых данных. Доведи MR до слияния.
```

Здесь `state` нужен при проектировании повтора, `migrate` — для старых данных,
`test` — при вызове API. Перед работой с MR подключается `watch-pr`,
перед слиянием — `merge`. [Условия выбора](skills.md).
