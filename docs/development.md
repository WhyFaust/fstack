# Разработка и релизы

## Структурная проверка

Для инструментов сопровождения нужны Python 3.12+ и PyYAML. Плагин не устанавливает
зависимости и не запускает сценарии при подключении.

```bash
python -m pip install -r requirements-dev.txt
python scripts/check_package.py
python scripts/release.py check
```

Автотесты и их данные удалены. CI проверяет структуру пакета на Ubuntu и Windows:
манифест, версии навыков, метаданные, роли, локальные ссылки и графику. Это не
поведенческая проверка модели, CLI, браузера или внешней интеграции.

## Изменить навык или роль

Редактируй исходники в `skills/` и `profile/agents/`. Сохраняй имена, границы
применения и разрешения. В описании навыка укажи, когда он нужен; подробности
отдельного режима храни в справке. Не ссылайся на абсолютные пути и версии кэша.
Роли выбирают навыки по именам `fstack:...` и доступным описаниям провайдеров.

`profile/config.example.toml`, `profile/AGENTS.md` и [руководство Codex](codex.md)
описывают профиль. `scripts/sync_profile.py` синхронизирует роли и управляемый блок
связей; чужие настройки, авторизация и MCP остаются у пользователя.

## Версии по Conventional Commits

| Коммит | Повышение |
| --- | --- |
| `fix:` или `perf:` | patch: `0.2.0` → `0.2.1` |
| `feat:` | minor: `0.2.1` → `0.3.0` |
| `!` в заголовке или `BREAKING CHANGE:` / `BREAKING-CHANGE:` | major: `0.3.0` → `1.0.0` |
| `docs:`, `chore:`, `ci:`, `build:`, `style:`, `refactor:`, `test:` без breaking change | Без релиза |

Scope поддерживается: `feat(profile): ...`. Из нескольких изменений берётся
наибольшее повышение. При squash merge Conventional Commit должен быть в итоговом
заголовке коммита. Версии вручную не повышай: `version` плагина и `metadata.version`
всех навыков меняются одним коммитом `chore(release): vX.Y.Z`.

## Публикация

После попадания в `main` workflow `.github/workflows/release.yml` проверяет пакет,
вычисляет версию и публикует GitHub Release с ZIP и SHA-256. Используется встроенный
`GITHUB_TOKEN` с `contents: write`; дополнительный токен не нужен. Правила ветки
должны разрешать workflow записывать коммит версии. Защиту ветки скрипт не обходит.

До первого релиза базой служит версия перед добавлением workflow; затем — последний
опубликованный стабильный релиз. Повторный запуск учитывает ожидающий коммит версии
и завершает принадлежащий workflow черновик без повторного повышения. Чужой черновик
или несовпадающий тег вызывают ошибку, а не перезапись.

Пробный расчёт после коммита workflow читает GitHub и ничего не публикует:

```bash
python scripts/release.py plan
```

`publish` разрешён скриптом только внутри workflow ветки `main`. Пользователю после
релиза нужно обновить источник, установить новую версию плагина, синхронизировать
роли через `fstack-setup` и начать новый чат. Команды — в [руководстве установки](installation.md).

Правила: [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).
