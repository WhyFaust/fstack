# Разработка, проверки и релизы

## Минимальные проверки

Для сопровождения нужны Python 3.12+, PyYAML из requirements-dev.txt
и Rust 1.90.0. Валидатор пакета собирается один раз из исходников.
Синхронизация профиля использует только стандартную библиотеку Python 3.11+.
Для защиты backup на Windows нужен встроенный Windows PowerShell: helper
задаёт через системный .NET API полную DACL до сохранения данных.

```bash
python -m pip install -r requirements-dev.txt
rustup toolchain install 1.90.0 --profile minimal --component rustfmt,clippy
cargo +1.90.0 build --release --locked --manifest-path tools/fstack/Cargo.toml
cargo +1.90.0 fmt --manifest-path tools/fstack/Cargo.toml -- --check
cargo +1.90.0 clippy --locked --manifest-path tools/fstack/Cargo.toml -- -D warnings
python scripts/check_package.py
python -m unittest discover -s scripts/tests -v
python scripts/release.py check
```

CI выполняет эти проверки на Ubuntu и Windows. Структурная проверка связывает
манифест, каталог и шаблон навыков, версии, UI-метаданные, роли, ссылки и PNG.
`scripts/check_package.py` сохраняет прежнюю команду и вызывает нативный
`fstack-check`; второй реализации валидатора на Python нет. Готовый исполняемый
файл можно указать через `FSTACK_CHECK_BIN`. Валидатор ничего не скачивает
и не собирает при запуске. Для обычного использования навыков, профиля и памяти
Rust не нужен. Синхронизация профиля и хранилище памяти остаются на Python.
Валидатор читает YAML 1.2: строки `yes`, `no`, `on`, `off` больше не считаются
логическими значениями. Для переносимости между инструментами заключай такие
строки в кавычки, а логические поля задавай как `true` или `false`.
В `scripts/tests` хранится только небольшой набор детерминированных регрессий
утилит: приватность backup, миграция управляемых ролей, конфликты и откат,
SemVer, идентичность релиза, восстановление draft, изоляция и жизненный цикл
памяти.
Внешние записи GitHub в тестах перехватываются; Git работает на временных репозиториях.
Модельных evals, тестов формулировок, больших фикстур и нового тестового фреймворка нет.

## Проверка фактическим клиентом

После сборки валидатора, в окружении с уже установленным Codex:

```bash
python scripts/check_installation.py
```

Путь к конкретному исполняемому файлу можно передать через --codex.
Скрипт создаёт отдельный временный CODEX_HOME, использует локальный marketplace,
проверяет установленную версию, идемпотентность helper, strict config и
обнаружение навыков и хуков памяти через app-server. UI-подсказки должны
ссылаться на имена, которые возвращает клиент. Для хуков проверяется состояние
до пользовательского одобрения. Собственный процесс останавливается,
временный профиль удаляется. Рабочий профиль пользователя не меняется.

Клиент может выполнять свои обычные служебные сетевые обращения; действуют
настройки доступа среды. Скрипт не устанавливает Codex, не вызывает модели
и не проверяет исполнение ролей: `model_tasks` и `role_execution` остаются
`not_run`. Проверка strict config не подтверждает доступность выбранных моделей
и уровней reasoning в аккаунте. Ошибка или недоступный клиент не считаются успехом.
Зафиксируй версию, ОС и результат; не распространяй вывод на все версии клиентов.
В CI без Codex выполняются пакетные проверки и регрессии скриптов; клиентская
проверка запускается в окружении с выбранной поддерживаемой версией.

## Структура навыков

Один небольшой навык даёт самостоятельный результат. В `description` от третьего
лица назови результат и ситуации, в которых он нужен. Сверь описание с типичным
запросом, перефразировкой и соседним сценарием, которому нужен другой метод.
Для нового навыка обнови `docs/skills.md`, UI и применимые ссылки ролей.

Новые и изменяемые навыки оформляй по
[единому шаблону](../skills/adapt-skill/references/template.md).
Порядок общих разделов проверяется валидатором; предметные шаги внутри них
остаются свободными. Форматирование без смены поведения не повышает версию.

Оставь в `SKILL.md` основной порядок работы, условия выбора и обязательные
проверки. Давай прямую относительную ссылку на справку рядом с условием, при
котором её нужно читать. Если справка превышает 100 строк, добавь в начале
оглавление. Общий контракт доказательств остаётся в `verify-result`.

Для рискованной операции укажи вход, проверку до действия и проверяемый
результат. При отказе укажи, на каком шаге остановиться и что перепроверить.
Для задач с несколькими допустимыми подходами достаточно критерия выбора.
Добавляй пример или шаблон там, где он разрешает неоднозначность. Для
исполняемого помощника укажи зависимости, способ запуска и смысл результата.

Проверяй работу из установленного пакета без Git-клона. В UI используй полное
имя из каталога клиента: например, $fstack:review-change. Не редактируй кэш.
Хуки памяти поставляются с пакетом и проверяются вместе с ресурсами
`use-memory`. Для прогонов используй временные vault и профиль Codex.
Настройки провайдеров Notion и RTK остаются внешними.

## Профиль и миграция ролей

Канонический источник управляемого блока — `profile/AGENTS.md`; helper читает
его из установленного пакета. Роли `auditor`, `coder`, `reviewer`, `verifier`
и `allure_analyst` задают границы работы. К однозначному методу исполнитель
переходит прямо; `select-skills` читает при необходимости выбора.
Поля `model` и `model_reasoning_effort` проверяются по типу и допустимому
формату. Выбор модели хранится в TOML, а не дублируется в коде валидатора.
Значения и приоритеты описаны в [контракте профиля](codex.md#модель-и-reasoning).

Состояние helper сохраняет `schema: 1` и допускает точный прежний либо новый
набор управляемых ролей. Для миграции проверяй минимальными регрессиями удаление
неизменённого управляемого `python_coder` после приватного резервирования,
конфликт изменённой или отсутствующей роли даже с `--adopt`, сохранение
неуправляемой копии и откат без перезаписи заново созданного файла.
JSON-результат сообщает `removed` и `unmanaged_retired`; инструкция перехода
находится в [руководстве установки](installation.md).

Синхронизация не переносит пример поверх `config.toml`. Setup согласует только
нужные поля, сохраняя авторизацию, провайдеры и личные настройки. Модельные сравнения
и автоматические evals не входят в проверки скриптов и без поручения не запускаются.

## SemVer и Conventional Commits

Публичный контракт включает имена методов и ролей, CLI утилит, схему профиля
и обещанное поведение установки. Выпускаются стабильные версии MAJOR.MINOR.PATCH.
Prerelease-канал пока не реализован. Версия манифеста обозначает выпуск пакета.
Workflow вычисляет её по Conventional Commits.

| Изменение | Коммит | Версия |
| --- | --- | --- |
| Исправление поведения или производительности | fix: / perf: | patch |
| Новая совместимая возможность | feat: | minor |
| Несовместимый публичный контракт | ! или BREAKING CHANGE: | major |
| Только пояснения, сопровождение без изменения поведения | docs: / chore: / ci: и аналогичные | Без релиза |

Файл Markdown может быть исполняемой инструкцией: изменение поведения SKILL.md
или роли оформляй как fix: или feat:, а не docs:. Для несовместимости в 0.x
этот проект также использует явное major-повышение. Scope поддерживается.
При squash итоговый заголовок должен сохранять Conventional Commit.

### Версии навыков

Автор PR повышает `metadata.version` каждого содержательно изменённого
навыка отдельно. Используй стабильный SemVer `X.Y.Z` и указывай одинаковое
значение в `SKILL.md` и всех его локализациях. Новый навык начинает с `1.0.0`.
При переходе на независимый SemVer ранее выпущенные навыки один раз
получают `1.0.0`. Их прежние версии обозначали выпуски пакета.
Версия навыка может быть выше версии пакета. Валидатор проверяет формат
SemVer и совпадение версий локализаций.

| Изменение навыка | Часть версии | Пример |
| --- | --- | --- |
| Исправление или уточнение поведения | PATCH | `1.0.0` → `1.0.1` |
| Совместимая новая возможность | MINOR | `1.0.0` → `1.1.0` |
| Несовместимое изменение публичного контракта | MAJOR | `1.0.0` → `2.0.0` |

Например, один из следующих выпусков пакета может включать навык A версии
`1.0.1` с исправлением, навык B версии `1.1.0` с новой возможностью и
неизменённый навык C версии `1.0.0`.
Изменения документации вне навыка и форматирование без изменения контракта
сами по себе повышения не требуют.

Workflow меняет только манифест коммитом `chore(release): vX.Y.Z`.
Поле `skills` в выводе `plan` показывает изменения в каталогах навыков
относительно последнего опубликованного релиза. Для этой диагностики
учитываются инструкции, локализации, UI, справки и ресурсы. Сравнение
frontmatter учитывает значения YAML и пропускает `metadata.version`.

Удаление публичной роли `python_coder` и источника `profile/links.md` вошло
в 2.0.0. Новые изменения выпускаются тем же workflow по Conventional Commits.

## Публикация

Матрица проверяет SHA события; release начинает с того же github.sha.
Скрипт сверяет исходный HEAD с GITHUB_SHA и читает живую main. Сторонний push
останавливает устаревший выпуск; обычный git push без force защищает от
последующей гонки. После изменения версии снова проверяется структура пакета.

Workflow публикует ZIP и SHA-256. Восстановление завершает только свой draft
с совпадающей ревизией; чужой draft или несовпадающий тег не перезаписываются.

Повтор того же run поддерживается и после записи коммита версии. Для такого
восстановления main должна быть единственным следующим коммитом после
проверенного SHA. Проверяются заголовок коммита, вычисленная SemVer-версия,
режим файла и побайтовое совпадение манифеста с ожидаемым обновлением из
проверенного исходника. Любое изменение другого файла отклоняется. При наличии
релиза также проверяется принадлежность его записи и маркер ревизии.
Завершённый выпуск повторно не публикуется.

Если main содержит другие изменения, нужен workflow их ревизии либо новый
workflow_dispatch на main через Actions → «Пакет и релиз» → Run workflow.
Служебный push с GITHUB_TOKEN сам по себе не запускает новый push-workflow
по [правилам GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

Пробный расчёт читает GitHub и ничего не публикует:

```bash
python scripts/release.py plan
```

publish допускается только в workflow main. После релиза пользователь обновляет
marketplace, пакет и роли и открывает новую сессию. Требования к защите main
описаны в [настройках репозитория](repository-settings.md).
