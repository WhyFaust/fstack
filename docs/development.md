# Разработка, проверки и релизы

## Минимальные проверки

Для разработки нужен Rust 1.90.0 и системный C/C++ toolchain для сборки SQLite.
Python не используется ни в runtime, ни в проверках. Пользователь устанавливает
пакет из `main` или готовый платформенный архив без средств разработки.
Для защиты backup на Windows нужен встроенный Windows PowerShell: helper
задаёт через системный .NET API полную DACL до сохранения данных.
Проверка DACL запускает системный PowerShell со своим поиском модулей,
не наследуя `PSModulePath` PowerShell 7: модули этого хоста несовместимы
с Windows PowerShell 5.1. Сами проверки владельца и закрытых прав сохраняются.

```bash
rustup toolchain install 1.90.0 --profile minimal --component rustfmt,clippy
cargo +1.90.0 build --release --locked --manifest-path tools/fstack/Cargo.toml
cargo +1.90.0 fmt --manifest-path tools/fstack/Cargo.toml -- --check
cargo +1.90.0 clippy --all-targets --locked --manifest-path tools/fstack/Cargo.toml -- -D warnings
cargo +1.90.0 test --release --locked --manifest-path tools/fstack/Cargo.toml
mkdir -p bin
cp tools/fstack/target/release/fstack bin/fstack
bin/fstack --package . check-package .
bin/fstack --package . release check
```

На Windows используй `fstack.exe`. CI выполняет проверки на Linux x64
(Ubuntu 22.04), Windows x64 и macOS Intel/Apple Silicon. Структурная проверка
связывает манифест, каталог и шаблон навыков, версии, UI-метаданные,
ссылки и PNG. `Cargo.lock` фиксирует зависимости. Для Windows CI задаёт
`RUSTFLAGS="-C target-feature=+crt-static"` и проверяет imports готового PE:
внешние VCRUNTIME/MSVCP и SQLite DLL не допускаются. Linux-сборка проверяет
зависимости glibc не выше 2.35. Бинарник ничего не скачивает
и не собирает при запуске. Пакет ищется по `--package` или относительно
исполняемого файла, без привязки к каталогу сборки.

Валидатор читает YAML 1.2: строки `yes`, `no`, `on`, `off` не считаются
логическими значениями. Для переносимости между инструментами заключай такие
строки в кавычки, а логические поля задавай как `true` или `false`.
UI проверяется в `agents/openai.yaml` и сопутствующих `openai_*.yaml`:
типы и длины полей, цвет, пути ресурсов, политика вызова и объявления
MCP-зависимостей. Обязательные поля UI и длина короткого описания 25–64 —
правила fstack, а не обязательные требования любого навыка Codex. Контракт
клиента и пределы проверки описаны в
[справке метаданных](../skills/adapt-skill/references/codex-metadata.md).

Регрессии в `tools/fstack/src/` и `tools/fstack/tests/` покрывают приватность
backup, миграцию управляемых ролей, конфликты и откат, SemVer, идентичность
релиза, восстановление draft, изоляцию и жизненный цикл памяти. Отдельная
проверка переносит пакет с бинарником и запускает проверку миграции и память с пустым
PATH. Для памяти временные vault и state должны находиться вне Git-workspace;
при искусственных Git-маркерах среды укажи чистый временный каталог через TMPDIR.
Внешние записи GitHub перехватываются; Git работает на временных репозиториях.
Модельных evals, тестов формулировок и отдельного тестового фреймворка нет.

В отчёте укажи, что именно проверил тест и что наблюдалось в клиенте.

## Проверка фактическим клиентом

После сборки и копирования бинарника в bin, в окружении с уже установленным Codex:

```bash
bin/fstack check-installation --codex /absolute/path/to/codex
```

Команда создаёт отдельный временный CODEX_HOME, использует локальный marketplace,
проверяет установленную версию, отсутствие новых глобальных ролей,
strict config и обнаружение навыков и хуков через app-server. Проверка пакета сверяет
основную ссылку каждой строки каталога с именем метода; проверка установки
сверяет состав файлов `skills/` и побайтно сравнивает их и `docs/skills.md`
с установленной копией, включая локализации, шаблоны и справки. UI-подсказки должны
ссылаться на имена, которые возвращает клиент. Для хуков проверяется состояние
до пользовательского одобрения. Собственный процесс останавливается,
временный профиль удаляется. Рабочий профиль пользователя не меняется.
Для проверки пути с символом `#` передай каталог пакета через `--package`.
При локальной регистрации используй источник `.` из этого каталога,
чтобы клиент не принял часть абсолютного пути после `#` за Git ref.

Клиент может выполнять свои обычные служебные сетевые обращения; действуют
настройки доступа среды. Команда не устанавливает Codex, не вызывает модели
и не исполняет поручения штатных агентов. Проверка strict config подтверждает
загрузку конфигурации клиента. Ошибка или недоступный клиент не считаются успехом.
Зафиксируй версию, ОС и результат; не распространяй вывод на все версии клиентов.
В CI без Codex выполняются пакетные проверки и нативные регрессии; клиентская
проверка запускается в окружении с выбранной поддерживаемой версией.

## Структура навыков

При создании или изменении навыка используй [adapt-skill](../skills/adapt-skill/SKILL.md).
[Шаблон](../skills/adapt-skill/references/template.md) задаёт проверяемые
разделы пакета. Новый навык внеси в `docs/skills.md`, добавь UI-метаданные
и обнови ссылки. Указывай в UI полное имя, которое возвращает каталог
клиента. Проверь метод и его ресурсы из установленного пакета.

Проверка Windows запускает команду из манифеста в cmd и Windows PowerShell.
Путь временного проекта содержит кириллицу, пробелы, `&` и квадратные скобки.
Входной JSON передаётся в UTF-8. Оболочка сохраняет рабочую папку до запуска
вложенного PowerShell, а нативный процесс наследует потоки ввода и вывода.
Тест сверяет ID найденной записи и текст ответа хука. Для коротких имён 8.3
отдельная проверка учитывает, поддерживает ли их том.

Хуки памяти поставляются с пакетом и проверяются вместе с ресурсами
`use-memory`. Для прогонов используй временные vault и профиль Codex.
Настройки провайдеров Notion и RTK остаются внешними.

## Миграция прежнего профиля

`migrate-profile` проверяет реестр прежнего профиля со схемой 1 или 2.
Регрессии покрывают неизменённые, изменённые и отсутствующие файлы,
сохранение неизвестных ролей и отказ при неподтверждённом владении.
Отдельно проверяются ссылки, приватность backup, байты вокруг прежнего
блока `AGENTS.md` и откат без перезаписи нового файла. Тесты сохраняют
правку, сделанную между проверкой хеша и перемещением файла, прерывают
миграцию после перемещения каждого вида файла и сверяют состав исходной
резервной копии при повторе. Общая блокировка исключает одновременную
запись прежнего помощника и миграции.
Сценарий из манифеста запускает фоновый хук с подготовленной сборкой.
Тест загрузки проверяет выбранный asset и отбрасывает неверный SHA-256.
[Поведение и команды миграции](codex.md#миграция-прежних-ролей).

## SemVer и Conventional Commits

Публичный контракт включает имена методов и ролей, CLI утилит, схему профиля
и обещанное поведение установки. Выпускаются стабильные версии MAJOR.MINOR.PATCH.
Prerelease-канал пока не реализован. Версия манифеста обозначает выпуск пакета.
Команда `release prepare` вычисляет версию по Conventional Commits до
слияния. Обнови рабочую ветку относительно текущей main и оформи изменения
Conventional Commits. Если ты продолжаешь править runtime, добавь последние
изменения в индекс Git до запуска команды. Задай в `PR_TITLE` точный заголовок PR.

```bash
bin/fstack --package . release prepare origin/main "$PR_TITLE"
git add .codex-plugin/plugin.json launchers/runtime-id
```

Включи оба сгенерированных файла в тот же PR. `launchers/runtime-id` хранит
SHA-256 записей дерева Git из индекса: имён, режимов и идентификаторов
объектов в `tools/fstack`, `hooks`, `launchers`, `.cargo`, `.gitattributes`
и workflow релиза. Сам файл идентификатора в расчёт не входит. Если два PR
выбрали одинаковый номер для разных изменений сборки, Git покажет конфликт
в этом файле. После объединения обнови версию и идентификатор командой
`release prepare` относительно актуальной базы.

Проверка `release check-next BASE TITLE` только сверяет результат. CI
передаёт SHA базы и заголовок PR и проверяет объединённое дерево.
Итоговый заголовок сохраняет самый высокий уровень изменений PR.
Изменение runtime, запускателей, хуков или workflow сборки требует как
минимум `fix:`. Исправления документации могут сохранить текущую версию.

| Изменение | Коммит | Версия |
| --- | --- | --- |
| Исправление поведения или производительности | fix: / perf: | patch |
| Новая совместимая возможность | feat: | minor |
| Несовместимый публичный контракт | ! или BREAKING CHANGE: | major |
| Только пояснения, сопровождение без изменения поведения | docs: / chore: / ci: и аналогичные | Без релиза |

Файл Markdown может быть исполняемой инструкцией: изменение поведения SKILL.md
или роли оформляй как fix: или feat:, а не docs:. Для несовместимости в 0.x
этот проект также использует явное major-повышение. Scope поддерживается.
При squash итоговый заголовок должен сохранять Conventional Commit.

### Версии навыков

Автор PR повышает `metadata.version` каждого содержательно изменённого
навыка отдельно. Используй стабильный SemVer `X.Y.Z` и указывай одинаковое
значение в `SKILL.md` и всех его локализациях. Новый навык начинает с `1.0.0`.
Версии навыков независимы от версии пакета. Исправление или уточнение
поведения повышает PATCH, совместимая новая возможность — MINOR,
несовместимое изменение публичного контракта — MAJOR.

Изменения документации вне навыка и форматирование без изменения контракта
сами по себе повышения не требуют.

Номер пакета меняется в том же PR, который меняет его контракт.
Поле `skills` в выводе `plan` показывает изменения в каталогах навыков
относительно последнего опубликованного релиза. Для этой диагностики
учитываются инструкции, локализации, UI, справки и ресурсы. Сравнение
frontmatter учитывает значения YAML и пропускает `metadata.version`.

## Публикация

Матрица собирает и проверяет SHA события. Для публикации workflow сверяет
HEAD с GITHUB_SHA и удалённой main, проверяет историю версий с последнего
выпуска и полный набор четырёх платформ. Каждый descriptor должен указывать
проверенный SHA, имя платформы и SHA-256 собранного бинарника.

Следующий PR вычисляет версию от манифеста текущей main, даже если его
релиз ещё не опубликован. Снимок main обращается только к URL своего выпуска. Во
время публикации нужный файл может временно отсутствовать; после публикации
следующий запуск подготовки получает его по тому же URL. Если следующий
merge опередил выпуск, старый workflow остановится и прежний номер может
остаться без опубликованных файлов. Тогда обнови marketplace до текущей main
и открой новый чат для подготовки актуальной версии.

Workflow создаёт черновик на проверенном SHA, загружает четыре ZIP, отдельные
платформенные бинарники и их SHA-256, затем публикует выпуск. Имя отдельного
бинарника и путь к кэшу содержат версию, идентификатор runtime и платформу.
Проверка PR и публикация пересчитывают идентификатор по проверенной ревизии,
включая запуски без нового выпуска. Файлы main
он не меняет. Контрольная сумма проверяет целостность скачанного файла.
Повтор загружает артефакты в собственный черновик этой версии и завершает
публикацию. Если после сбоя в main попало только пояснение, workflow сверяет
исходники runtime, запускатели, хуки и конфигурацию сборки с ревизией
черновика и сохраняет его исходный тег и содержимое пакета. При расхождении
тега, владельца, маркера или исходников публикация останавливается.
Если прямой push обошёл PR и внёс неверное повышение SemVer, `release plan`
покажет первый ошибочный коммит main после последнего тега. Обычный повтор
проверяет ту же историю; для восстановления владельцу потребуется отдельно
согласовать восстановительный выпуск с проверенными SHA и артефактами.
Уже опубликованный выпуск остаётся неизменным. Новый выпуск использует
собственный номер, устаревшие черновики сохраняются.

Пробный расчёт читает GitHub и ничего не публикует:

```bash
bin/fstack --package . release plan
```

`publish` выполняется в workflow main. Клиент получает новый пакет при запуске,
а фоновый хук подготавливает бинарник этого выпуска. Требования к защите main
описаны в [настройках репозитория](repository-settings.md).
