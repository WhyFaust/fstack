# Разработка и выпуск

## Минимальные проверки

Для разработки нужны Rust 1.90.0, системный C/C++ toolchain для сборки SQLite
и Python 3.12 или новее. Cargo загружает закреплённую ревизию fmem. После
обновления этой зависимости сверяй Cargo.lock и уведомления в
`tools/fstack/native-runtime.json`. Установи компоненты Rust и зависимости
тестов в рабочее окружение Python. Из корня репозитория выполни команды ниже.

```bash
rustup toolchain install 1.90.0 --profile minimal --component rustfmt,clippy
python -m pip install -r tools/fstack/evals/requirements.txt
python .github/workflows/check.py
```

Команда проверяет форматирование, Clippy и тесты Rust, собирает релизный бинарник,
сверяет пакет, локальные ссылки, якоря и метаданные версии. Затем она запускает
тесты измерителя и корпуса. Бинарник появится в `tools/fstack/target/release/`
под именем `fstack`, на Windows под именем `fstack.exe`.

[CI](../.github/workflows/release.yml) задаёт платформы и флаги сборки. Он передаёт
этой же команде бинарник выпуска и целевую платформу. Тесты Python, сравнение
версии с базой и проверка установки выполняются в задаче Linux. В задачах Windows
и macOS команда сообщает о пропуске тестов Python. Проверяй память во временных
vault и профиле вне Git.

## Проверка фактическим клиентом

Подготовь отдельную копию проверяемой ревизии и добавь в неё собранный бинарник
по пути `bin/fstack` или `bin/fstack.exe` для Windows.

```bash
tools/fstack/target/release/fstack --package /absolute/path/to/package check-installation --codex /absolute/path/to/codex
python tools/fstack/evals/check_doctor.py /absolute/path/to/package --codex /absolute/path/to/codex
python tools/fstack/evals/check_skill_invocation.py /absolute/path/to/package --codex /absolute/path/to/codex
```

Проверки используют отдельный профиль. Первая сверяет установленную версию,
навыки и хуки. Вторая проверяет `doctor` до установки, после установки и после
одобрения хуков. Третья читает запросы клиента к локальной заглушке:

- обычный чат и обсуждение названий сохраняют выключенный режим;
- прямой вызов передаёт выбранную инструкцию; в цитате клиент тоже может
  приложить файл, поэтому проверяется правило о цитировании;
- включение передаёт имена и условия выбора всех установленных навыков.
  Продолжение обходится без повторного индекса. Выключение и соседний чат
  проверяются отдельно.
- в постоянном чате выбор `ultra` передаёт координатор и каталог на текущий
  ход. Проверяются смена глубины, приоритет ручных команд и временный чат.

CI устанавливает Codex CLI из npm-тега `latest` и выводит версию в журнал. Чтобы проверить действия
модели на GitLab MR, дай ей снимок на чтение и сверь по журналу, что чтение
`watch-pr/SKILL.md` предшествовало обращению к MR. Модельные прогоны требуют поручения.

В Desktop проверь обычный ход без записи (`phase: skipped`) и поправку из поля
ввода (`memory stage`, затем запись с правильным `session_id`). Для поручения Codex
и подагента проверь поиск, `memory report` на первом `Stop` или `SubagentStop`
и сохранение на следующем. Прерванный ход и Plan пропускают запись. При смене
формата журнала повтори сценарии.

Чтобы проверить выбор глубины самой моделью, в Desktop на `ultra` передай
во время работы явный вызов `$fstack:faust-mode` и поручи отдельному агенту
найти имя плагина в манифесте. В родительском журнале проверь следующий
`spawn_agent` с `fork_turns="none"` и `reasoning_effort="low"`. В журнале этого
исполнителя проверь `turn_context.payload.effort == "low"`, затем сверь его
ответ с именем из манифеста.

## Изменение навыка

Сверь [формат](../skills/skill/SKILL.md), [каталог](skills.md) и локализации.
При адаптации пройди [исходный сценарий и контрольный случай](../skills/skill/SKILL.md#перенести-рабочий-метод).
В отчёте покажи, какое решение принял исполнитель в каждом случае. Уведомления
в поставке относятся к фактически включённым материалам и зависимостям.

## Версии и публикация

Заполни [шаблон PR](../.github/PULL_REQUEST_TEMPLATE.md). Исправление повышает
PATCH, возможность или несовместимость в серии 0.x — MINOR. Для MAJOR требуется
прямое указание и изменение [package-major](../launchers/package-major).

Добавь входы сборки в индекс Git, затем выполни:

```bash
tools/fstack/target/release/fstack --package . release prepare VERSION
git add .codex-plugin/plugin.json launchers/package-version launchers/runtime-id
```

Без аргумента `release prepare` пересчитывает идентификатор для выбранной версии.
Новая версия нужна для изменений навыков, каталога, манифеста, интерфейса,
marketplace, лицензий и входов сборки. CI сверяет базу PR, имя выпуска в GitHub
Releases и коммит очереди слияния.

Изменения `.github/workflows/` сначала слей отдельным PR. CI берёт команду проверки
из ревизии PR и проверяет уже выпущенный пакет, если всё дерево за пределами
workflow совпадает с его тегом.
Для заметок к выпуску опиши действия пользователя в разделе PR `## При обновлении`.

1. Для выпуска новой версии дождись успешной сборки четырёх платформ на текущем SHA открытого Ready PR.
   Если `main` изменился, обнови ветку и повтори проверки.
2. После ревью владелец или мейнтейнер оставляет в PR отдельный комментарий
   `/fstack-release <полный SHA>`.
   Это разрешает выпуск именно этой ревизии. Издатель берёт бинарники успешного PR run,
   загружает в черновик четыре ZIP, четыре бинарника и восемь файлов SHA-256,
   сверяет их и публикует тег.
3. После успеха «Подготовить выпуск» слей проверенный PR. С этого момента
   marketplace на `main` раздаёт новую версию с уже доступными файлами.
   Затем CI повторно сверяет релиз, назначает `latest` и обновляет зеркало
   `stable` для подключённых к нему клиентов. При сбое повтори запуск.

Издатель собирается из закреплённой ревизии в workflow. Для изменения его логики
сначала проверь и закоммить исходники и тесты, затем укажи проверенный полный SHA
в шаге «Получить исходники издателя» и пересчитай `runtime-id`.
